# 정리컴파일러 — 바이브코딩 마스터 프롬프트

## 0. 역할과 작업 방식

너는 이 프로젝트의 제품 설계자이자 시니어 풀스택 엔지니어다. 아래 요구사항을 읽고, 실제로 실행·검증할 수 있는 웹앱을 개발하라. 사업소개용 랜딩페이지나 버튼만 있는 목업으로 끝내지 마라.

프로젝트의 가칭은 ‘정리컴파일러’, 코드명은 `organization-compiler`다. 한국어 사용자 경험을 기본으로 하되 코드와 데이터 필드 이름은 영어로 작성한다.

기존 저장소가 있으면 먼저 README, AGENTS.md, package.json, lockfile, 현재 브랜치, 변경 파일, 테스트, 배포 설정을 확인하라. 기존 작업을 무단 삭제하거나 다른 프로젝트를 덮어쓰지 마라. 저장소가 없으면 독립된 새 작업 폴더에서 시작하라.

사소한 선택 때문에 계속 질문하지 말고, 아래 기본값으로 진행하면서 가정을 기록하라. 다만 계정 접근, 유료 서비스 결제, 개인정보의 외부 전송, 기존 데이터 삭제, 운영 배포처럼 권한과 영향이 큰 작업은 별도 승인 없이 실행하지 마라.

전체 방향을 이해하되 한 번에 모든 기능을 얕게 만들지 마라. 첫 실행에서는 문서와 화면 구성만 만들지 말고, 아래 ‘1단계’의 입력→계산→배치→목록→저장 흐름까지 실제로 연결하라.

## 1. 제품의 정의

우리가 만드는 것은 ‘수납함 쇼핑몰’도, ‘사진을 깔끔하게 바꿔주는 이미지 생성기’도 아니다.

사용자의 공간, 물건, 생활습관을 이해하고 다음 순서로 문제를 해결하는 도구다.

공간과 물건 입력
→ 정리 문제 파악
→ 정리 아이디어·전략 제안
→ 사용자가 전략 선택
→ 정리 방식과 시각적 스타일 선택
→ 실제 제품 후보와 배치를 함께 계산
→ 적합성 검증
→ 대안 비교·수정
→ 구매목록과 정리 실행 가이드
→ 저장·재계산

가장 중요한 원칙은 ‘어떤 박스를 살까?’보다 ‘이 물건들을 어떻게 관리해야 할까?’를 먼저 결정하는 것이다.

사용자가 이미 가지고 있는 수납함을 재사용하거나, 새 수납함 없이 물건의 위치만 바꾸는 안도 정상적인 결과여야 한다. 매출을 만들기 위해 모든 정리 문제를 구매로 해결하지 마라.

최종 성공 기준은 예쁜 결과 이미지가 아니라 다음 질문에 답하는 것이다.

‘무엇을, 어떤 기준으로 나누어, 어디에 넣고, 어떤 제품을 몇 개 구입하며, 실제로 어떻게 정리하면 되는가?’

브랜드 로고, 상품 이미지, 디자인 파일, 소스코드 등을 무단 복제하지 마라. 상품 데이터와 에셋의 이용 조건을 확인하고 출처를 기록하라. 오픈소스를 도입할 때도 라이선스와 유지보수 상태를 확인하라.

특정 플래너에 충돌 검사, 정밀 공차 계산, AI 정리 기능 등이 있다고 직접 확인 없이 기록하지 마라. 그러한 기능은 ‘우리가 구현할 요구사항’과 구분한다.

시장에 경쟁 제품이 없다는 전제로 개발하거나 ‘세계 최초’ 같은 검증되지 않은 문구를 사용하지 마라.

## 3. 제품 원칙

1. 정리 전략이 상품 추천보다 먼저다.
2. 공간 적합성과 생활 편의성이 시각적 스타일보다 우선한다.
3. 기존 물건과 수납함의 재사용을 정식 선택지로 제공한다.
4. 치수·수량·가격·충돌 판정은 코드가 계산한다. 언어모델이 숫자를 만들어 확정하지 않는다.
5. 공간의 내측 치수, 제품의 외측 치수, 제품의 내측 치수를 구분한다.
6. ‘들어감’, ‘설치 가능’, ‘열고 꺼낼 수 있음’, ‘물건이 수납됨’은 별도 검사다.
7. 모르는 값은 unknown으로 유지한다. 빈 값을 0이나 통과로 바꾸지 않는다.
8. 치수에 맞는 실제 판매 옵션이 없으면 그 사실을 보여준다. 가상의 상품을 만들지 않는다.
9. 도면, 상품목록, 가격, 실행 가이드는 동일한 계획 스냅샷에서 생성한다.
10. 초기에는 좁은 공간 유형에서 전 과정을 완성한다. 범위 축소와 허위 완료를 혼동하지 않는다.
11. AI 연결이 없어도 기본적인 정리 전략 제안과 계산은 작동해야 한다.
12. 안전 또는 필수 제약을 위반한 안을 ‘조금 불편하지만 추천’으로 통과시키지 않는다.

## 4. 첫 출시 범위와 확장 범위

첫 번째 완성 대상은 ‘기존 수납장 안의 직육면체 한 칸’이다. 책장, 팬트리, 장난감장처럼 이미 존재하는 수납공간을 대상으로 한다.

처음부터 방 전체의 가구 배치나 벽체 시공을 해결하지 않는다. 한 칸을 완성한 후 여러 칸으로 확장할 수 있도록 데이터 구조만 준비한다.

초기 완성 범위:
- 치수 직접 입력과 선택적인 사진 첨부.
- 물건 종류·수량·사용빈도·보관 상태 입력.
- 기존 수납함 등록.
- 규칙 기반 정리 전략 제안과 사용자 선택.
- 기능적 정리 방식과 시각적 스타일의 분리.
- 오픈형 박스, 트레이, 파일형 수납 등 단순한 제품의 배치.
- 직육면체 장애물, 허용 방향, 여유 공간, 기본 접근 경로 검사.
- 실제 좌표를 사용하는 평면도·정면도.
- 상품 수량·예상 비용·미확인 항목·구매 링크·실행 순서.
- 로컬 저장, 불러오기, 프로젝트 복제, JSON 내보내기.

후속 게이트를 통과한 뒤 추가:
- 뚜껑형 제품과 서랍의 개폐 궤적.
- 선반 추가 및 적층 구조의 지지·호환성 검증.
- 일반 서랍 내부 정리.
- 여러 칸, 문 경첩, 배관이 있는 공간.
- AI 사진 분석, 3D 보조 뷰, 클라우드 동기화.
- 판매처 연동, 공급사 카탈로그, 주문 연결.

초기 범위 밖의 공간을 선택하면 ‘아직 정밀 검증을 지원하지 않는 공간’이라고 표시한다. 미지원인데 비슷한 그림만 그려 지원한 척하지 마라.

## 5. 사용자 여정

첫 화면의 중심 행동은 ‘공간 정리 시작하기’다. ‘샘플로 체험하기’도 제공한다. 회원가입을 먼저 요구하지 않는다.

A. 공간 입력
사용자가 폭·깊이·높이를 입력한다. 안쪽 치수를 재도록 안내하고, 사진 없이도 진행되게 한다.

B. 물건과 생활 입력
물건의 종류, 수량, 사용빈도, 대략적인 부피 또는 실제 치수, 함께 사용하는 물건, 이미 가진 수납함을 입력한다.

C. 정리 아이디어 선택
수납 제품을 보여주기 전에 ‘사용빈도별’, ‘활동별’, ‘재고와 사용 중 물건 분리’, ‘최소 구매’ 같은 전략을 설명한다. 왜 이 사용자에게 맞는지 입력값에 근거해 보여준다.

D. 정리 방식·스타일 선택
오픈형·숨김형·혼합형, 한 번에 꺼내기·카테고리별 분리 같은 사용 방식을 선택한다. 색상·재질·투명도 등 시각적 스타일은 별도 선택한다.

E. 대안 계산·비교
가능하면 2~3개의 실질적으로 다른 안을 제시한다. 예: 최소 구매안, 접근성 우선안, 외관 통일안. 가능한 안이 하나면 하나만, 없으면 진단을 보여준다.

F. 배치 수정
상품 선택, 숫자 입력 또는 드래그로 배치를 수정한다. 수정할 때마다 적합성·수량·가격을 재검증한다.

G. 실행
구매목록, 재사용할 물건, 미확인 사항, 설치·정리 순서를 함께 보여준다. 사용자가 완료 여부를 체크하고 다음에 다시 열 수 있어야 한다.

간편 모드에서는 최소 입력으로 시작하되 결과를 ‘개략 계획’으로 표시한다. 정밀 모드의 입력을 하지 않았는데 확정적 적합 판정을 주지 마라.

## 6. 입력 모델과 측정 규칙

공간:
- 이름, 공간 유형, 실제 사용 가능한 내부 폭·깊이·높이.
- 전면 개구부의 폭·높이와 위치. 내부보다 입구가 좁을 수 있다.
- 앞쪽에서 물건을 꺼낼 때 사용할 수 있는 외부 공간.
- 바닥·선반 등 실제 지지면.
- 장애물과 접근 금지 영역.
- 측정 출처, 측정 오차 또는 불확실성.

물건:
- 이름, 카테고리, 수량, 사용빈도.
- 실제 보관 상태의 치수. 접은 옷과 펼친 옷을 같은 치수로 취급하지 않는다.
- 무게, 세워 보관해야 하는지, 눕혀도 되는지, 함께 보관할 그룹.
- ‘치수 확인’, ‘대략적 그룹’, ‘미측정’을 구분.
- 수량 미상과 수량 0을 구분.

기존 수납함:
- 소유 수량, 외경, 내경, 허용 방향, 상태, 사용할 수 있는 공간.
- 사용 가능한 재고 수량을 넘겨서 재사용 배치하지 않는다.
- 이름만 같은 서로 다른 크기의 수납함을 합치지 않는다.

사용자 제약:
- 예산과 예산이 절대 상한인지 선호인지.
- 숨김형·오픈형 선호, 시각적 스타일.
- 손쉽게 꺼내기, 라벨 사용, 새로운 구매 최소화 등 우선순위.
- 선택적으로 접근 가능한 높이, 무거운 물건의 취급 제한 등 사용성 요구.

단위:
- UI는 cm와 mm를 지원하되 내부 기하 계산은 정수 mm로 통일한다.
- 60cm와 600mm를 동일하게 처리한다.
- 초기 입력 정밀도는 1mm로 명시하고, 그보다 작은 단위 입력은 조용히 반올림하지 않는다.
- 음수, NaN, Infinity, 치수가 0인 물체, 비정상적으로 큰 입력을 거절한다.
- 위치 좌표 0은 정상값이다.
- 수량은 정수, 초기 가격은 KRW 정수로 처리한다.

치수를 여러 지점에서 측정했다면 보수적인 유효값을 사용한다. 사진에서 추정한 치수는 사용자가 직접 확인하기 전까지 확정 치수로 승격하지 않는다.

## 7. 정리 전략 엔진

초기에는 테스트 가능한 규칙 기반 엔진을 구현한다. 문장만 바꾼 동일한 추천 3개를 생성하지 마라.

전략의 예:
- 사용빈도별 분리: 매일 쓰는 것과 비축품을 분리.
- 활동별 묶음: 함께 쓰는 물건을 한 그룹으로 배치.
- 최소 구매: 기존 수납함과 직접 배치를 우선 사용.
- 한 동작 접근: 자주 쓰는 물건을 꺼내기 위해 다른 박스를 이동하지 않게 구성.
- 외관 통일: 기능 제약을 통과한 뒤 색상·재질·형태의 일관성을 우선.

각 전략은 다음을 구조화한다.
- 적용한 사용자 입력.
- 묶을 물건과 분리할 물건.
- 전면·후면 등 영역 배분.
- 선호하는 수납 기본 요소.
- 장점과 불편한 점.
- 확인이 필요한 가정.
- 적용된 ruleId 목록.

기능적 정리 스타일과 시각적 스타일을 혼합하지 마라.
예를 들어 ‘화이트 미니멀’은 시각적 스타일이지 정리 전략이 아니다. ‘사용 중 물건은 전면, 비축품은 후면’은 정리 전략이다.

사용자가 고정한 전략과 다른 전략으로 바꿔야 문제가 해결된다면 변경안을 설명하고 선택받는다. 몰래 전략을 바꾸지 않는다.

사용자가 물건을 버리거나 처분하겠다고 선택하지 않는 한, 배치에 실패한 물건을 결과에서 삭제하지 마라.

## 8. 수납 기본 요소와 조합 규칙

제품명에 직접 종속되지 않는 `StoragePrimitive`를 정의한다.

초기 구현:
- directPlacement: 별도 수납함 없이 직접 배치.
- openBin: 오픈형 박스.
- tray: 트레이.
- verticalFile: 파일형 수납.

확장 대상:
- closedBin, drawerUnit, divider, shelfRiser, verticalRack.
- turntable, hangingBasket, wallSystem 등은 별도 지원 조건이 필요하다.

각 primitive에 필요한 외형·접근성·지지·내용물 제약을 정의한다. 미구현 primitive는 자동 추천 후보에서 제외한다. 아이 안전·유해물질·고하중 등 안전 판정이 필요한 요청은 치수 적합성과 분리한다. 필요한 안전 조건을 검증하지 못한 제품이나 배치를 안전한 해결책으로 추천하지 마라.

제품 조합은 `Recipe`로 정의한다. 예: ‘전면 사용품 트레이 + 후면 재고 박스’. Recipe는 영역, 물건 그룹, 허용 primitive, 필수 제약, 설명 템플릿을 가진다.

정리함 안에 물건을 넣는 문제와 정리함을 수납장 안에 넣는 문제를 모두 표현하라. 박스가 들어간다고 그 안의 모든 물건도 들어간 것으로 처리하지 마라. 부피의 합이 작다는 것만으로 개별 물건의 수납 가능성을 판정하지 않는다.

## 9. 컴파일 파이프라인과 책임 분리

구조는 다음과 같다.

Input
→ Normalize / Validate
→ Organization IR
→ Strategy Selection
→ Style Constraints
→ Recipe + Catalog Candidates
↔ Layout Search
→ Independent Validation
→ Ranked Alternatives
→ Immutable Plan Snapshot
→ Diagram / BOM / Action Guide

SKU 선택과 배치는 단방향 파이프라인으로 분리하지 않는다. 실제 판매 치수 때문에 배치를 다시 탐색할 수 있어야 한다.

예를 들어 이상적인 폭 197mm 박스를 먼저 가정하고 나중에 상품을 찾는 방식만 구현하지 마라. 카탈로그의 실제 후보 치수로 가능한 배치를 계산하고, 결과가 없으면 다른 후보나 조합으로 되돌아가라.

필수 도메인:
Project, Space, ItemGroup, OwnedContainer, Strategy, StyleProfile,
ProductVariant, Offer, Placement, ItemAssignment, ConstraintCheck,
PlanSnapshot, BOMLine, ActionStep, Evidence.

공유 데이터 계약에 포함할 개념:
- `CheckStatus = pass | fail | unknown | not_applicable`
- `DataOrigin = synthetic | manufacturer | retailer | user_measured | ai_estimated`
- 치수값, 단위, 불확실성, 출처를 묶은 측정 데이터.
- 외경과 내경을 별개로 가진 제품 옵션.
- 구조물 배치 좌표와 내용물 배치 좌표의 부모 참조.
- 원본 입력 revision과 카탈로그·규칙·solver 버전.

스키마를 한 곳에서 정의하고 런타임 검증과 TypeScript 타입이 어긋나지 않게 관리하라. 핵심 모델에 any를 사용하거나 오류를 숨기는 타입 단언으로 통과시키지 마라.

## 10. 기하학 모델

좌표계를 명시한다.
- 원점: 수납공간 내부의 전면·왼쪽·아래.
- x: 왼쪽→오른쪽.
- y: 전면→후면.
- z: 아래→위.
- width=x, depth=y, height=z.

렌더링, 저장, solver, 테스트가 같은 좌표계를 사용해야 한다. 용기 내부의 물건은 부모 용기 기준 좌표를 가지며, 전역 좌표 변환을 명시한다. 부모 참조의 순환과 동일 물건의 중복 배정을 거절한다.

부모 용기의 외형과 자식 물건의 외형이 겹치는 것을 일반 충돌로 처리하지 마라. 대신 자식이 사용 가능한 내측 공간에 포함되는지, 용기의 벽·칸막이나 다른 자식과 충돌하는지 검사한다. 안쪽으로 좁아지는 제품은 확인된 보수적 내측 공간을 사용하고, 확인할 수 없으면 미확인으로 남긴다.

초기 모델은 축에 정렬된 직육면체와 직사각형 지지면을 사용한다. 2D 화면을 제공하더라도 데이터와 충돌 판정은 깊이와 높이를 포함해야 한다.

회전은 제품이 허용하는 방향만 사용한다. 기본값은 세운 상태에서 수평 0도이며, 확인된 제품만 90도 수평 회전을 추가한다. 깊이와 높이를 바꿔 서랍을 옆으로 눕히는 식의 해를 만들지 마라.

경계 접촉과 안전 여유를 구분한다. 수학적으로 면이 닿는 것과 실제로 설치할 여유가 충분한 것은 같은 판정이 아니다.

기본 검사:
A. 제품의 외형이 내부 경계를 벗어나지 않는가?
B. 제품끼리 또는 장애물과 부피가 겹치지 않는가?
C. 바닥·선반 등 지지면이 존재하는가?
D. 허용된 방향으로 놓였는가?
E. 전면 입구를 통과하는 지원된 설치 경로가 있는가?
F. 제품 또는 내용물을 꺼내기 위한 접근 공간이 있는가?
G. 내용물이 실제 내경 안에 들어가는가?
H. 알려진 하중·적층·설치 조건을 위반하지 않는가?

초기 설치 경로는 ‘허용 방향을 유지한 전면 직선 삽입’처럼 지원 범위를 명시하라. 경로를 찾지 못했다고 모든 회전·분해·재조립 경로가 불가능하다고 단정하지 마라.

서랍이나 뚜껑을 추가할 때는 닫힌 상태의 크기만 검사하지 않는다. 이동 중 차지하는 영역을 검사하고, 데이터가 없으면 개폐 확인 필요로 처리한다.

임의의 상자를 공중에 띄우지 마라. 적층은 확인된 지지·호환 규칙이 있을 때만 허용한다. 서로 다른 제품이 크기만 같다고 적층 가능하다고 가정하지 마라.

## 11. 여유 공간과 불확실성

벽면 여유, 제품 사이 여유, 손으로 잡는 여유, 개폐 여유를 서로 다른 파라미터로 관리한다. 렌더링용 그림자나 시각적 간격을 실제 기하 여유로 사용하지 마라.

예시 fixture의 5mm 같은 숫자는 테스트용 설정이지 모든 제품에 적용되는 설치 기준이 아니다. 제조사 조건이 있으면 출처와 함께 별도 관리한다.

판정은 다음을 구분한다.
- 명목 치수에서의 적합.
- 입력한 오차 범위까지 고려한 보수적 적합.
- 필요한 치수 또는 설치 조건의 미확인.

보수적 검사에서는 공간은 작은 쪽 경계, 제품은 큰 쪽 경계로 계산한다. 치수 오차와 별도 설치 여유를 혼동하거나 두 번 차감하지 않도록 테스트하라.

필요한 오차 정보가 없는데 오차 0으로 간주하여 ‘정밀 검증 완료’로 표시하지 마라.

사용자 문구 예:
‘입력한 치수 기준으로 배치 가능합니다. 제품 손잡이 돌출과 실측 오차는 아직 확인되지 않았습니다.’

‘무조건 맞습니다’, ‘100% 완벽한 수납’ 같은 물리적 보증 문구를 사용하지 마라.

## 12. 탐색과 대안 비교

처음부터 범용 3D 최적화 엔진을 만들지 마라. 지원 범위 안에서 Recipe 기반 후보 생성, 실제 SKU 필터링, 결정론적 배치 탐색, 제한된 backtracking을 구현한다.

정확한 제약 검증은 초기부터 필요하지만, 전역 최적해 보장은 초기 목표가 아니다.

진행 순서:
1. 명백히 맞지 않는 상품과 옵션 제거.
2. 기존 수납함과 직접 배치 후보 포함.
3. 선택한 전략에 맞는 Recipe 생성.
4. 실제 상품 치수로 배치 후보 탐색.
5. 외경·내용물·경로·지지·수량 검사.
6. 실패 후보 제거, unknown 항목은 별도 표시.
7. 살아남은 후보를 목적별 비교.
8. 동등하거나 사실상 같은 안은 중복 제거.

우선순위는 강제 제약 충족→사용자 목표→비용·스타일 등의 선호 순서다. 저렴하거나 예쁘다는 이유로 충돌을 무시하지 않는다.

초기 비교 지표:
- 신규 구매 비용과 배송비 확인 상태.
- 재사용한 수납함 수.
- 배정한 물건 수와 미배정 수. 수량 미상은 별도.
- 자주 쓰는 물건을 꺼내기 위해 먼저 이동해야 하는 다른 용기 수.
- 외관 통일 조건의 충족 여부.
- 확인되지 않은 치수·설치 조건 수.

‘접근성 94%’ 같은 근거 없는 점수를 만들지 마라. 점수를 도입한다면 산식·입력·가중치·해석을 문서화하고, 실험으로 검증된 효과와 구분한다.

면적 점유율, 외형 부피 점유율, 실제 수납 용량은 다르다. 하나를 다른 것처럼 보여주지 않는다. 큰 빈 박스를 넣어 점유율만 높이는 안을 좋은 정리로 평가하지 마라.

동일 입력·카탈로그·규칙·solver 버전·탐색 예산이면 동일 결과를 재현하도록 한다. 후보 순서와 동률 해소 규칙을 명시한다.

벽시계 시간뿐 아니라 탐색 노드 수 등 결정론적인 작업 한도를 둔다. 중단된 탐색은 ‘현재 탐색 범위에서 찾은 안’으로 표시한다.

해를 못 찾으면 ‘제품 없음’, ‘측정 부족’, ‘예산 충돌’, ‘지원하지 않는 배치’, ‘탐색 한도 도달’을 구분한다. 제한된 탐색 실패를 수학적 불가능으로 표현하지 마라.

## 13. 실제 상품 카탈로그

데이터를 반드시 세 층으로 분리한다.

ProductVariant: 실제 물리적 제품 옵션. 브랜드, 상품명, 옵션명, 식별자, 외경, 내경, 재질, 색상, 허용 방향, 설치 조건 등.

Offer: 해당 옵션을 판매하는 판매처의 가격·재고·구매 URL·묶음 수량·배송 조건·확인 시각.

OwnedContainer: 사용자가 이미 소유한 수납함과 사용 가능 수량.

배송 박스 크기를 제품 외경으로 사용하지 마라. 뚜껑 포함 크기인지, 손잡이 돌출을 포함했는지, 가장 좁은 내경인지 구분한다.

가격과 치수는 필드별로 출처와 확인 상태를 가질 수 있어야 한다. 상품 페이지를 찾았다는 것만으로 모든 필드를 검증 완료로 처리하지 않는다.

초기 데이터 전략:
- 개발·테스트용 합성 제품 20개 내외를 준비한다.
- 모두 `synthetic`으로 표시하고 가짜 실제 브랜드·구매 링크를 붙이지 않는다.
- 실제 상품 등록은 수동 입력과 검증된 CSV/JSON import로 시작한다.
- 출시 전에는 첫 지원 공간을 충분히 검증할 수 있는 작은 실제 카탈로그를 확보한다.
- 실제 상품 데이터가 확보되지 않으면 ‘데모 카탈로그 모드’라고 명시한다.

처음부터 모든 쇼핑몰을 크롤링하지 마라. 임의 URL에서 옵션·가격·치수가 자동 추출된다고 가정하지 않는다. 초기에는 URL을 참고 링크로 저장하고 확인된 필드를 직접 등록하는 흐름이면 된다.

내경이 없으면 외경만으로 내용물 수납까지 확정하지 않는다. 가격 미상과 0원, 재고 미상과 구매 가능을 구분한다.

같은 상품의 색상·규격·판매 묶음 옵션을 혼동하지 않는다. 비슷한 이름으로 다른 옵션을 구매 링크에 연결하지 마라.

## 14. 구매목록과 실행 가이드

BOM은 화면에 놓인 물체 수와 실제 주문 수량을 구분한다.

예:
필요 수납함 5개 / 판매 단위 2개 묶음
→ 주문 3묶음 / 실제 배송 6개 / 남는 수납함 1개.

이미 가진 수납함은 구매 비용에서 제외하지만 배치와 재사용 목록에는 남긴다. 뚜껑·칸막이·레일 같은 필수 부품이 별매라면 누락하지 않는다. 세트에 포함된 부품을 다시 더해 이중 결제 비용으로 계산하지 마라.

가격에는 다음을 구분해 표시한다.
- 확인된 상품 소계.
- 확인된 배송비.
- 미확인 배송비와 가격.
- 조건부 할인 여부.
- 가격 확인 시각.

배송비가 미확인인데 총액 확정이라고 표시하지 않는다. 여러 판매처의 배송비는 판매처 단위로 계산하되 검증된 정책만 사용한다.

초기 구매 기능은 ‘구매목록’과 ‘판매처에서 보기’다. 실제 연동이 없는데 여러 쇼핑몰의 장바구니에 담았다고 표시하지 마라. 결제 자동 실행은 범위 밖이다.

실행 가이드는 동일 PlanSnapshot의 ID와 배치 좌표에서 생성한다.
예: 공간 비우기→분류하기→기존 수납함 배치→새 제품 배치→물건 이동→라벨→미배정 물건 확인.

가이드의 각 단계는 해당 영역·용기·물건 그룹으로 연결되어야 한다. 아직 구입하지 않은 제품은 도착 전 완료 상태가 되지 않도록 한다.

## 15. 결과와 상태 관리

계획 결과는 최소한 다음 상태를 가진다.
- 입력 보완 필요.
- 계산 중.
- 배치안 있음.
- 조건부 배치안: 일부 정보 확인 필요.
- 현재 조건에서 추천 가능한 안을 찾지 못함.
- 입력 변경으로 재계산 필요.

단일 ‘통과’ 배지 대신 검사 범위를 나눈다.
외경 배치 / 내용물 수납 / 설치·접근 / 지지·하중 / 가격·재고 확인.

하나의 검사에서 pass가 나왔다고 나머지도 pass로 만들지 마라. not_applicable은 해당 검사가 적용되지 않는다는 근거가 있을 때만 사용한다.

각 결과에 inputRevision, catalogVersion, ruleVersion, solverVersion을 기록한다. 입력이 바뀌면 이전 결과를 최신 결과로 보여주지 않는다.

Worker 요청에는 revision 또는 requestId를 붙인다. 오래 걸린 과거 계산 결과가 나중에 도착해 최신 결과를 덮어쓰지 않게 한다.

확정된 계획은 스냅샷으로 저장한다. 카탈로그 가격이 바뀌어도 과거 견적을 조용히 수정하지 말고 새로고침·재계산을 통해 새 버전을 만든다.

## 16. 화면과 디자인 방향

일반적인 AI 채팅창이 아니라 ‘수납 계획을 만드는 작업대’를 설계하라.

분위기:
따뜻한 미니멀, 차분한 제품 카탈로그, 정밀한 설계 도구. 과한 그라데이션·네온·유리 효과·무관한 실내 사진으로 기능 부족을 가리지 않는다.

제안 팔레트:
배경은 따뜻한 오프화이트, 본문은 짙은 차콜, 강조는 절제된 세이지 계열. 색상은 디자인 토큰으로 관리하고 실제 대비를 검사한다.

폰트는 읽기 좋은 한국어 시스템 폰트를 우선 사용한다. 숫자와 단위는 정렬과 가독성을 특별히 신경 쓴다.

데스크톱 플래너:
- 상단: 프로젝트명, 저장 상태, 현재 단계, 실행 취소·다시 실행.
- 좌측: 공간·물건·전략 입력.
- 중앙: 정면도·평면도 전환, 실제 치수와 배치.
- 우측: 선택 제품, 적합성 검사, 대안.
- 하단 또는 별도 탭: 구매목록과 정리 가이드.

모바일:
가로로 줄인 데스크톱 UI를 만들지 않는다. 단계별 입력과 전체 너비 도면, 선택 항목용 하단 패널, 고정된 다음 행동 버튼을 사용한다.

필수 화면:
시작 / 프로젝트 목록 / 공간 입력 / 물건 입력 / 전략 선택 /
방식·스타일 선택 / 대안 비교 / 배치 편집 / 구매목록·실행 /
상품 수동 등록·import / 측정 가이드.

빈 상태, 계산 중, 실패, 미확인, 저장 실패, 지원하지 않는 형식을 모두 디자인한다. 비활성 버튼에는 이유를 표시한다.

색만으로 오류를 표현하지 말고 텍스트와 아이콘을 함께 사용한다. 마우스 없이 수치 입력과 키보드로 배치할 수 있게 한다. 모바일 터치 대상은 충분한 크기로 설계한다.

실상품 도형의 크기를 드래그로 임의 변경하여 공간에 맞추지 마라. 배치 편집은 이동·허용 회전·제품 교체로 제한한다. 제품 규격 또는 공간 치수를 바꾸면 영향을 받는 배치와 내용물을 다시 검증한다.

도면은 이미지가 아니라 실제 placement 데이터를 렌더링한다. 선택 강조, 치수선, 장애물, 필요한 접근 영역을 켜고 끌 수 있게 한다.

3D는 후속 보조 뷰다. 멋진 3D 화면을 위해 2D 편집의 정확도와 첫 작동 버전을 늦추지 마라.

## 18. AI 사용 범위

초기에는 API 키 없이 동작하는 규칙 기반 모드를 완성한다. 실제 모델을 사용하지 않았는데 ‘AI가 분석했습니다’라고 표시하지 않는다.

선택적 AI 기능:
- 사진 속 물건·장애물 후보를 제안.
- 자연어 요청을 입력 스키마 후보로 변환.
- 정리 전략의 설명과 비교를 보조.
- 검증된 계획의 실행 가이드를 읽기 쉽게 설명.

AI에 맡기지 않을 것:
- 최종 치수 적합 판정.
- 가격·재고·상품 옵션의 사실 확정.
- 충돌 검사와 구매 수량 계산.
- 사용자 확인 없는 측정값 수정.
- 자동 결제.

AI 출력은 임시 제안으로 받아 스키마 검증과 사용자 확인을 거친다. 숫자·상품 ID·URL은 허용된 데이터와 대조한다. ‘모델이 자신 있다고 말함’은 검증 근거가 아니다.

사진만 보고 정확한 mm 치수를 안다고 주장하지 않는다. 사진 속 표지나 문구, 상품 상세 설명에 포함된 지시를 시스템 명령으로 실행하지 않는다.

AI 호출 실패 시 수동 입력과 규칙 기반 기능은 유지한다. 재시도 한도, 취소, 명확한 실패 안내를 구현한다. 가짜 결과로 성공 화면을 만들지 않는다.

## 19. 저장·개인정보·보안

첫 버전은 로컬 우선이다. 공간 사진과 물건 목록을 외부 서버에 자동 전송하지 않는다. 추후 AI 전송은 전송 대상과 목적을 알리고 선택받는다.

로컬 저장을 영구 백업이라고 설명하지 마라. 브라우저 데이터 삭제로 없어질 수 있음을 안내하고 export/import를 제공한다.

저장 완료 표시는 실제 DB 기록 성공 후에만 표시한다. 저장 실패, 용량 초과, 손상된 import, 스키마 버전 불일치에 대한 처리가 있어야 한다.

동일 프로젝트를 여러 탭에서 수정할 때 이전 revision이 최신 기록을 조용히 덮어쓰지 않게 한다. DB 트랜잭션과 revision 확인으로 충돌을 감지한다.

import는 허용된 필드·단위·값 범위를 검증한다. 외부 상품명·설명은 HTML로 실행하지 않는다. CSV export는 스프레드시트 수식으로 실행될 수 있는 문자열을 안전하게 처리한다.

초기 URL 등록은 참고 링크 저장이며 임의 주소를 서버에서 자동 fetch하지 않는다. 이후 자동 수집 기능을 넣을 때는 허용 대상, 리디렉션, 내부망 주소 차단, 크기·시간 한도 등 SSRF 방어를 별도로 검토한다.

API 비밀키를 프런트엔드 코드, 공개 저장소, 로그에 넣지 않는다. 공개 앱에 외부 AI를 연결할 때는 서버 측 adapter와 사용량 제한을 마련한다.

프로젝트 삭제와 사진 삭제가 실제 저장 데이터에 반영되는지 테스트한다. 선택적 통계 수집은 사진·물건명·집 내부 정보가 기본 수집되지 않도록 설계한다.

## 20. 반드시 포함할 검증 사례

아래 수치는 실제 판매 상품이 아니라 합성 테스트 fixture다. solver와 별도로 검증기에 직접 넣는 테스트도 작성하라.

T01. 단위 변환
60cm와 600mm 입력이 같은 공간 모델과 결과를 만든다.

T02. 정상 배치
폭 600mm 공간, 좌우 여유 각각 5mm, 제품 사이 여유 각각 5mm.
폭 190mm 제품 3개를 같은 방향으로 한 줄 배치하면
190×3 + 5×2 + 5×2 = 590mm이므로 폭 조건을 통과한다.
다른 축·경로 조건은 별도 fixture에서 충족시킨다.

T03. 경계 초과
같은 조건에서 폭 195mm 제품 3개는
195×3 + 5×2 + 5×2 = 605mm이므로 거절한다.
그림 크기를 줄이거나 gap을 몰래 줄여 통과시키지 않는다.

T04. 내부 수납 실패
제품 외부 높이 250mm, 내부 높이 230mm일 때 높이 240mm 물건의 세운 수납을 거절한다.

T05. 입구 통과 실패
공간 내부에는 들어가지만 허용 방향에서 제품 폭이 전면 개구부보다 큰 경우, 지원된 직선 삽입 경로 검사를 통과시키지 않는다.

T06. 장애물 충돌
최종 배치가 장애물의 부피와 겹치면 거절한다. 화면 뒤쪽에 가려져도 동일하다.

T07. 허용하지 않은 회전
눕히면 들어가는 제품이라도 방향 정책이 허용하지 않으면 거절한다.

T08. 지지면 없음
충돌은 없지만 공중에 있는 제품을 정상 배치로 인정하지 않는다.

T09. 불확실성
명목 치수에서는 맞지만 입력된 공간·제품 오차를 반영하면 초과하는 사례를 구분한다. 오차 미상은 오차 0과 다르게 처리한다.

T10. 기존 수납함 수량
보유 2개인 제품을 3개 재사용 배치하지 않는다. 추가 1개를 구매할 수 있으면 별도 구매 항목으로 표시한다.

T11. 구매 묶음
필요 5개, 판매 2개 묶음이면 3묶음 구매·6개 확보·1개 잉여를 계산한다.

T12. 미확인 데이터
내경 미상, 가격 미상, 배송비 미상, 재고 미상을 각각 올바르게 표시한다. 어느 것도 자동으로 0 또는 통과가 되면 안 된다.

T13. 물건 보존
입력된 모든 물건은 배정 또는 미배정 목록에 남는다. 수량이 계산 과정에서 사라지거나 중복되지 않는다.

T14. 대안 부족
가능한 안이 1개면 1개만 출력한다. 3개의 카드 수를 맞추려고 가짜 차이를 만들지 않는다.

T15. 결과와 목록 일치
도면의 제품과 BOM의 물리적 수량이 일치한다. 구매 묶음 때문에 발생한 잉여는 별도로 설명된다.

T16. 저장 복원
저장→새로고침→불러오기 후 치수, 전략, 배치, 물건 배정, 스냅샷 버전이 유지된다.

T17. 오래된 계산 응답
연속 입력 변경 후 이전 Worker 응답이 늦게 도착해도 최신 계획을 덮어쓰지 않는다.

T18. 실패와 복구
저장 실패, 잘못된 import, AI 미연결, 검색 취소, 탐색 한도 도달에서도 기존 프로젝트가 손상되지 않는다.

T19. 개폐 확장 게이트
서랍·뚜껑 제품을 활성화하기 전에 닫혀 있을 때는 맞지만 열 때 충돌하는 테스트를 추가하고 실패를 검출한다.

T20. 브라우저 흐름
샘플 시작→치수 수정→전략 선택→계산→상품 변경→구매목록→저장→재접속 전체 흐름을 실제 브라우저에서 검증한다.

속성 테스트:
통과한 결과의 경계·충돌·수량 보존·허용 방향 불변조건을 무작위 입력으로 검사한다. 검증기의 일부는 탐색 코드와 독립된 단순 계산으로 교차 확인한다.

## 21. 단계별 개발과 완료 게이트

0단계 — 조사와 최소 설계
기존 코드 확인, 레퍼런스 검토, 지원 범위 확정, 좌표·단위·데이터 계약 정의, 첫 fixture 작성.
완료 조건: 구현할 첫 사용자 흐름과 검증 기준이 명확하다. 문서만 계속 확장하지 않는다.

1단계 — 실제로 작동하는 세로 연결
한 칸 입력→물건 그룹→규칙 기반 전략 선택→방식·스타일 선택→합성 카탈로그 배치→도면→수량·비용→저장·불러오기를 연결한다.
데모라는 표시는 유지하되 계산과 저장은 진짜로 작동해야 한다.
완료 조건: 핵심 기하·수량 테스트와 브라우저 대표 흐름이 통과한다.

2단계 — 실용적 상품 매칭
실상품 수동 등록·import, 필드별 출처, 내경·입구·접근 검사, 기존 수납함 재사용, 판매 묶음·배송비·미확인 처리, 구매 링크와 실행 가이드를 완성한다.
완료 조건: 검증된 실제 상품을 사용한 사례를 재현할 수 있다. 실제 카탈로그 미확보 시 이 단계 완료를 주장하지 않는다.

3단계 — 편집 품질과 배포 준비
드래그·숫자 편집·실행 취소, 대안 비교, 모바일 사용성, 오류 복구, 출력물, 접근성, 성능을 개선한다.
완료 조건: 지원 환경에서 주요 작업을 오류 없이 끝낼 수 있고 테스트·빌드·실제 화면 검증 근거가 있다.

4단계 — 선택적 고도화
AI 입력 보조, 서랍·뚜껑, 여러 칸, 3D, 클라우드 동기화, 판매처 연동을 하나씩 게이트를 두고 추가한다.

단계 번호가 높다고 품질이 좋은 것이 아니다. 정확하게 작동하는 좁은 범위를 유지하면서 넓혀라.

## 22. 성능과 품질 기준

아래는 측정해야 할 개발 목표이며 이미 달성한 수치가 아니다.

초기 대표 부하: 한 칸, 상품 후보 약 100개, 배치 용기 최대 20개 수준의 fixture를 준비하고 실행 환경을 기록한다. 내용물 수량에 대해서도 별도 한도를 둔다.

기본 배치 변경은 체감상 즉시 반영되도록 하고, 전체 탐색은 UI를 막지 않게 한다. 예시 목표로 기본 검사 100ms 이내, 대표 탐색 2초 내 첫 유효안 등을 사용할 수 있으나 실제 측정 전 성능 주장에 쓰지 마라.

중단·취소·부분 결과가 있어야 한다. 큰 입력에서 브라우저가 멈추기보다 지원 한도와 대안을 알려주는 것이 낫다.

360~390px 모바일, 768px 태블릿, 1280~1440px 데스크톱에서 핵심 화면을 확인한다. 가능하면 주요 브라우저에서 검증하고 미검증 환경을 구분한다.

CI에는 typecheck, lint, 단위·통합 테스트, 핵심 브라우저 테스트, build를 포함한다. 테스트를 삭제하거나 의미 없는 assert로 바꿔 통과시키지 않는다.

## 23. 작업 기록과 정직한 보고

다음 문서를 필요한 깊이만큼 유지한다.
- README.md: 실행·테스트·지원 범위·제약.
- AGENTS.md: 반드시 지킬 불변조건과 작업 규칙.
- docs/PRODUCT_SPEC.md: 사용자 흐름과 범위.
- docs/ARCHITECTURE.md: 데이터 계약·좌표·모듈·결정사항.
- docs/REFERENCES.md: 공식 링크, 실제 확인 내용, 미확인 사항.
- docs/IMPLEMENTATION_STATUS.md: 완료·미완료·테스트·다음 단계.

변경은 작고 검증 가능한 단위로 진행한다. 저장소가 있으면 기능 브랜치를 사용하고 사용자의 기존 변경을 보존한다. 원격 push·배포 여부는 해당 환경의 권한과 사용자 지시에 따른다.

보고에는 실제 수정 파일, 실행 명령, 성공·실패 결과, 알려진 한계, 실행 방법을 포함한다. 실행하지 못한 검사는 ‘미실행’이라고 적는다.

커밋 SHA, 배포 URL, 스크린샷, 테스트 통과 수를 만들어내지 마라. 실제 배포가 없으면 로컬 실행과 배포 완료를 구분한다.

대화가 끊겨도 재개할 수 있도록 현재 상태와 다음 작업을 저장소에 남긴다. 대화의 기억보다 저장소의 코드·테스트·문서를 기준으로 삼는다.

## 24. 장기 방향과 지금 하지 않을 일

장기적으로는 ‘정리 전략→실제 상품→구매→실행→사용 피드백’의 연결을 강화한다.

추가할 수 있는 기능:
여러 브랜드 카탈로그, 판매처별 주문 연결, 배송 후 정리 확인, 수납 위치 검색, 재정리, 호환 제품 추천, 공급사 데이터 제공, 자체 제품 카탈로그.

다만 첫 버전에서 자체 제조·재고 운영·물류·마켓플레이스까지 구현하지 않는다. 향후 자체 제품도 동일 ProductVariant와 Offer 구조로 들어가도록만 한다.

제휴 수수료나 자체 제품 판매가 생겨도 치수 적합성·안전·사용자 제약의 판정을 바꾸지 않는다. 광고와 추천 근거를 구분한다.

지금 하지 않을 것:
근거 없는 전시장 수준 3D, 모든 가정공간 지원, 무제한 쇼핑몰 크롤링, 자동 결제, 전역 최적해 보장, 사진만으로 정확한 실측, 검증되지 않은 안전 보증.

## 25. 지금 시작할 구체적 작업

이제 위 내용을 이해한 뒤 실제 작업을 시작하라.

1. 기존 작업 환경과 코드 상태를 확인한다.
2. 첫 사용자 흐름과 최소 데이터 계약을 짧게 정리한다.
3. 단위·치수·충돌·수량 계산의 첫 테스트를 만든다.
4. 한 칸의 입력과 합성 카탈로그를 연결한다.
5. 규칙 기반 정리 전략과 방식·스타일을 선택하고 실제 배치안을 생성한다.
6. 배치도·BOM·저장·불러오기를 한 흐름으로 완성한다.
7. 실제 브라우저에서 사용해 보고 문제를 수정한다.
8. 무엇이 작동하고 무엇이 아직 없는지 근거와 함께 보고한다.

계획을 다시 설명하는 답변으로 끝내지 마라. 실행 환경에서 코드를 수정할 수 있다면 1단계 구현을 수행하라. 외부 서비스가 없다는 이유로 로컬에서 가능한 구현까지 멈추지 마라.

반대로 실행 환경 자체가 없다면 구현·테스트·배포를 했다고 주장하지 마라. 제공 가능한 코드와 검증 방법, 실제 미실행 범위를 명확히 구분하라.

최우선 원칙:
‘그럴듯한 추천보다 검증 가능한 배치, 박스 판매보다 실제 정리 문제 해결.’
