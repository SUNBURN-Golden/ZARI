# ZARI 빈 공간에 맞는 수납함 찾기

- 요청 기준: 준태님 지시, **2026-11-05 13:15 KST**. ZARI의 메인 기능으로 설계한다.
- 상태: **설계 초안**. 구현·실상품 검증·화면 승인·배포 완료를 의미하지 않는다.
- 이번 작업은 이 문서만 작성한다. 다른 파일 변경, 커밋, 네트워크 요청은 하지 않는다.
- 외부 사이트·API·약관·모델·요금의 최신 상태는 조회하지 않았다. 아래 외부 조건은 도입 전 확인 대상이다.
- 요청에 명시된 API 제약은 설계 전제로 사용하며, 실제 이용 권한 확보와 구분한다.

## 1. 목표와 범위

사용자가 빈 공간의 **가로(W)·깊이(D)·높이(H), cm**만 입력하면 맞는 수납함과 조합을 찾는다.
한 개, 같은 제품 여러 개의 가로·앞뒤·위아래 배치, 서로 다른 제품의 혼합 배치를 모두 다룬다.
첫 지원 판매처는 **무인양품 + 다이소**이며, 이후 오늘의집 → 네이버쇼핑 → 쿠팡 → 29cm → IKEA → 추가 판매처 순으로 확장한다.
쇼핑몰 수를 늘려도 치수·옵션 식별과 출처 검증을 생략하지 않는다.

### 목표

- 물건 치수·방 종류·가입·사진 없이 숫자 세 개와 버튼 하나로 시작한다.
- 수집한 카탈로그의 적격 수납함을 모두 검사하고, 모든 일치 상품을 끝까지 열람할 수 있게 한다.
- 조합은 배치 수량·방향·좌표·남는 공간·확인할 조건을 함께 제공한다.
- 앱의 카탈로그 공급원은 Cloudflare R2 하나로 고정한다. 로컬 캐시는 R2 스냅샷의 사본이다.
- 별도 봇과 Chrome 확장이 수집을 자동 수행한다. 일반 사용자는 확장을 설치하지 않는다.
- 치수 추출과 조합 순위 보조에는 서버 측 DeepSeek Flash를 사용하고, 최종 계산은 Rust가 맡는다.

### 비목표

- 방 전체 설계, 비직육면체 공간의 정밀 계산, 사진/OCR, 상품 이미지·썸네일·로고 수집.
- 로그인·CAPTCHA·차단 우회, 비공개 API 역공학, 자동 장바구니·결제·주문.
- 외경만으로 내용물 수납량·내경·하중·안전·개폐 가능성을 보증하는 기능.
- 한국의 모든 판매 상품이나 연속 좌표의 모든 배치를 이미 확보했다는 주장.
- 기본 웹 빌드에 DuckDB·Polars·Python·CUDA를 추가하는 작업.

### “ALL”의 제품 계약

- **상품 전체**: 선택된 R2 release의 모든 shard와 모든 적격 옵션을 검사한다. 상위 몇 개만 검색하지 않는다.
- 같은 물리 옵션의 판매처는 묶어 보이되, 모든 출처·판매 제안을 펼쳐 볼 수 있다.
- 치수 부족·출처 충돌·품절·미수집은 별도 건수로 남긴다. 미확인을 “안 맞음”으로 세지 않는다.
- **조합 전체**: 선언된 방향·배치 패턴·수량 범위 안에서 중복을 제거한 조합을 대상으로 한다.
- 기본 혼합 탐색은 예산이 있으므로 전체 열거를 보장하지 않는다. 미탐색 범위와 이어보기를 제공한다.
- `complete`는 해당 release와 명시한 탐색 범위만 완주했다는 뜻이다. 전체 쇼핑 시장의 완전성을 뜻하지 않는다.
- 무제한 혼합 배치 전체 열거는 후속 과제다. 제한을 숨긴 채 “모든 조합”이라고 출시하지 않는다.

기존 수집기의 실제 Chrome·사이트·R2 연결은 문서상 미검증이며 합성 fixture 시험과 구분한다.

기존 `VerificationScope::Verified`도 import 결과의 `VerificationStatus::Confirmed`를 만들지 않는다.
v1의 `high` 추출 신뢰도는 확인 완료가 아니며, 현재 내경은 unknown으로 변환된다.

## 3. 사용자 흐름

1. “빈 공간에 맞는 수납함을 찾아요” 아래 가로·깊이·높이 입력과 cm 단위를 보여 준다.
2. “안쪽을 재 주세요. 깊이는 앞에서 뒤까지예요.”를 안내한다. 입력 예시는 placeholder로만 둔다.
3. **“맞는 수납함 찾기”** 한 번으로 입력 검증, R2 자료 읽기, Rust 계산을 시작한다.
4. 캐시가 있으면 그 버전의 결과를 먼저 보여 주고 자료 확인 날짜를 표시한다.
5. 결과는 **딱 맞음 / 조합** 두 그룹으로 보여 주고, 각 그룹에서 더 보기를 제공한다.
6. 상품은 “크기·남는 자리·판매처”, 조합은 “A 2개 + B 1개·놓는 방법”을 먼저 보여 준다.
7. 펼치면 도형·정확한 옵션·방향·가격 확인 날짜·치수 근거·미확인 조건을 읽을 수 있다.
8. “판매처에서 보기”는 사용자가 누른 외부 이동이다. 앱이 판매처를 미리 조회하지 않는다.
9. 공간을 고치면 이전 결과에 “크기를 바꿨어요. 다시 찾아 주세요.”를 표시한다.

처음 화면에 추가 질문을 강제하지 않는다. 여유·회전·판매처 필터는 결과 뒤 “조건 바꾸기”로 연다.
오류나 오프라인에서도 세 입력을 보존한다. 기존 `zari.easy.v1`을 새 형식으로 조용히 덮어쓰지 않는다.
새 초안은 버전이 다른 키로 저장하고, 기존 물건 비교 화면·전문가 프로젝트는 독립적으로 유지한다.

## 4. 데이터 모델과 확인 상태

아래는 **v2 제안 계약**이다. Rust DTO/Schemars에서 TS 타입·검증기를 생성하며 별도 TS 도메인을 만들지 않는다.
기존 Product → ProductVariant → Offer와 Evidence/Provenance를 정본으로 사용한다.
수집 원문과 확인 이벤트는 입력 근거이며 앱이 상태 문자열만 믿고 Confirmed를 만들 수 없다.

| 필드/레코드 | 의미와 제약 |
|---|---|
| `schemaVersion`, `catalogVersion`, `catalogDigest` | 스키마 호환성과 불변 카탈로그 식별 |
| `productId`, `variantId`, `sourceProductId`, `sourceOptionId` | 모델·실물 규격·원본 옵션 식별; 이름만으로 병합 금지 |
| `name`, `brand`, `category`, `optionLabel` | 짧은 상품 텍스트; 한국 판매 옵션을 구분 |
| `outer.width/depth/height` | 각 축의 정수 mm 명목값, 오차, 출처, 확인 상태 |
| `inner.width/depth/height` | 독립 사실; 없으면 unknown, 외경에서 추정 금지 |
| `dimensionRole`, `rawText`, `rawUnit` | 외경/내경/포장 치수 구분과 짧은 원문 근거 |
| `handles`, `lidState`, `effectiveEnvelope` | 손잡이·뚜껑 포함 여부; 중복 가산 금지 |
| `allowedOrientations` | 근거가 있는 upright0/upright90; 미확인은 별도 |
| `stackability`, `compatibility`, `load` | 적층 가능 여부·최대 단수·호환 제품·하중 사실 |
| `stackPitchMm` | 끼워지는 적층의 실제 추가 높이; 단순 H 곱과 분리한 신규 사실 |
| `source.site/host/url`, `fetchedAt` | 수집 위치·시각; HTTPS·허용 호스트만 |
| `source.method`, `parserVersion`, `textHash` | extension/API/허용 feed, 추출 버전, 변경 감지 |
| `confidence` | 필드별 high/medium/low/unparsed 및 추출 근거; 참일 확률로 표시하지 않음 |
| `extraction.model/promptVersion` | AI를 실제 썼을 때만 모델·프롬프트 버전 기록 |
| `status` | unconfirmed/confirmed/quarantined; 외경 확인 상태의 요약 |
| `verification` | 필드별 검사자 또는 rule ID·버전·근거 hash·검사 시각·판정 |
| `freshness`, `lastSeenAt`, `withdrawnAt` | 신선도와 판매 종료를 확인 상태와 별개로 관리 |
| `offerId`, `sellerId`, `productUrl` | 물리 옵션 하나에 여러 판매처 연결 가능 |
| `packQuantity`, `packPriceKrw`, `shipping`, `inventory` | 개당/묶음 가격 구분, unknown과 0 분리 |
| `affiliate`, `disclosureText`, `priceObservedAt` | 제휴 여부·노출 문구·관측 시각 |

어느 레코드에도 이미지 바이트·이미지 URL·스크린샷·쿠키·회원정보를 포함하지 않는다.
포장 규격은 근거 역할로만 보관하며 외경 후보로 사용할 수 없다. 긴 설명·후기는 보관하지 않는다.
원본에 축·단위·옵션 연결이 없으면 숫자를 추측하지 않는다. `30×20×10`만으로 W/D/H를 확정하지 않는다.
축별 혼합 단위는 각각 명시된 경우에만 Rust가 정규화하고, 1mm 미만 정밀도는 임의 반올림하지 않는다.

### 확인 전이

1. 모든 신규 관측은 `unconfirmed`로 생성한다. AI와 정규식 어느 쪽도 바로 승격하지 않는다.
2. Rust가 양수·상한·정수 정밀도·내경≤외경·옵션 대응·출처 형식을 검증한다.
3. 사람 검토 또는 승인된 사이트별 규칙이 외경의 세 축·단위·옵션·돌출 포함 범위를 확인한다.
4. 규칙 확인은 권위 있는 명시 사양과 독립적으로 대조한다. AI 출력 재파싱만으로 확인하지 않는다.
5. 확인 이벤트가 원문 hash와 필드 값에 결속된 경우에만 게시자가 `confirmed` 자료를 만든다.
6. 규격·옵션·사양 원문이 바뀌면 영향받은 확인을 무효화하고 다시 `unconfirmed`로 돌린다.
7. 상충 출처·옵션 재사용·비정상 수치는 `quarantined`로 격리하고 공개 release에 넣지 않는다.

외경 confirmed여도 내경·오차·적층·설치가 confirmed라는 뜻은 아니다. 확인된 명목 치수도 공차는 unknown일 수 있다.
미확인 항목은 “치수 확인 중”으로 조회 가능하되 확인된 추천 수에 넣지 않는다. 조건부 계산은 별도 표시한다.
단순 사이트 이름·서명·hash는 치수 사실의 증명이 아니다. 발행자 신뢰와 사실 검증을 따로 검사한다.

무인양품·다이소의 실제 호스트·상품 URL 패턴은 이번에 조회하지 않았다. 추측한 도메인을 활성 allowlist에 넣지 않는다.
기존 후보는 `ohou.se`, `store.ohou.se`, `www.29cm.co.kr`, `www.ikea.com/kr/`이며 현행 허용 근거는 재확인한다.
새 사이트는 정확한 호스트·경로·redirect 정책·확장 권한·Rust URL 검증을 함께 갱신한다. wildcard 전체 허용은 금지한다.

### 공식 API 경로 평가

- 네이버 검색 API는 상품 발견과 판매 링크·가격 연결에 유용하다. 제목의 숫자를 확정 치수로 사용하지 않는다.
- 검색 결과 링크의 목적지는 별도 판매처다. allowlist와 수집 허용 근거가 없으면 자동 방문하지 않는다.
- 쿠팡 Partners는 승인된 제휴 통로로 평가한다. 응답에 치수가 없으면 별도 허용된 사양 근거가 필요하다.
- 쿠팡 승인 전에는 동작한다고 가정하지 않는다. 미승인·차단을 브라우저 우회 수집으로 대체하지 않는다.
- 제휴 링크 옆에 경제적 이해관계를 명시하고 현행 요구 문구·노출 위치를 도입 시 확인한다.
- 양 API의 quota·비용·재배포·캐시 보존기간·가격 표시 조건은 공식 약관으로 확인하며 수치를 추정하지 않는다.
- API가 이미지 필드를 반환해도 경계에서 버린다. 비밀키는 서버 환경에만 두고 R2/확장/앱에 배포하지 않는다.
- 공식 API는 서버 봇의 별도 adapter이며 일반 웹페이지 fetch 크롤러로 확대하지 않는다.

### 자동 수집 운영

`허용 시드 → 봇 작업 큐 → Chrome 확장 → 제한된 텍스트 → 규칙/AI 추출 → Rust 검증 → 확인 → R2 게시`.
초기 설치·허용 설정 뒤 목록 발견, 옵션 분리, 정제, 게시까지 클릭 없이 실행한다. 모호한 건만 검토 큐에 남긴다.
자동화는 확인 단계를 없앤다는 뜻이 아니다. 검토 대기 중에도 다른 적격 항목은 독립 배치로 처리할 수 있다.
Chrome은 로그인 없는 전용 프로필과 보이는 창을 사용한다. Native Messaging와 0600 소켓·확장 ID 고정을 재사용한다.
동시에 한 게시자만 동작한다. 현재 기본값인 호스트별 8초+지터, 실행당 100쪽, 일일 300건을 초기 상한으로 삼는다.
robots의 더 긴 지연과 사이트별 더 낮은 한도를 우선한다. robots를 읽지 못하면 해당 호스트를 닫는다.
로그인·CAPTCHA·403/429·금지 신호가 나오면 호스트를 중지하고 실패 상태를 보존한다. 우회·자동 재시도하지 않는다.
기존 cooldown 뒤 재시도 동작은 그대로 승계하지 않는다. 재개는 운영자가 근거를 확인한 새 실행으로 한다.
수집 refresh는 승인된 유한 작업의 일정으로 운영한다. 상태 polling·실패 반복 실행·중복 타이머를 만들지 않는다.
kill switch와 출처별 제거를 유지한다. PC/Chrome이 꺼져 있으면 자동 수집도 중단되며 갱신 지연으로 표시한다.

공개 페이지·robots 허용·사실 데이터라는 이유만으로 자동 수집과 재배포 권한이 생기지는 않는다.
약관·데이터베이스권·저작권·제휴 계약을 출처별로 확인하고 허용 범위와 검토 날짜를 기록한다.
이미지에만 있는 규격은 OCR로 보충하지 않는다. 허용 텍스트 사양 제공 또는 별도 실측 확인을 기다린다.

## 6. Rust 적합성·조합 알고리즘

### 입력과 단일 상품

- UI는 cm 십진수 문자열 세 개만 보낸다. Rust `parse_length` 계열로 1mm 단위 정규화한다.
- 0·음수·NaN·무한대·범위 초과·과도한 소수 자릿수는 구조화된 오류로 반환한다.
- `easy_fit.rs`의 `evaluate_probe` 기반 축 비교와 한국어 차이 표현을 공통 helper로 재사용한다.
- 기존 `EasyFitResult` 하나로 새 검색 결과를 포장하지 않는다. 별도 versioned SpaceFit 입력/결과 DTO를 둔다.
- W=x(좌→우), D=y(앞→뒤), H=z(아래→위), 원점은 공간 안쪽의 전면·왼쪽·아래다.
- 모든 적격 variant에 허용된 방향을 적용하고 외경·돌출을 합친 유효 envelope를 비교한다.
- `Upright0`와 `Upright90`만 MVP 회전 후보로 삼는다. 가로/깊이만 바꾸고 높이는 유지한다.
- 눕히기·뒤집기·임의 각도는 제외한다. 방향 허용 사실이 없으면 후보의 회전 검사는 unknown이다.
- 기본 조회는 명목 치수에 의한 개략 결과다. 3개 입력만으로 보수적 적합까지 확인했다고 표시하지 않는다.

### 오차와 여유

공간은 `S_min = nominal − minus_uncertainty`, 제품은 `b_max = nominal + plus_uncertainty`로 계산한다.
벽면 양쪽 여유 `c_left/c_right`, 제품 사이 간격 `g`, 손 넣기·개폐 여유는 서로 다른 사실이다.
오차 또는 필수 여유가 unknown이면 보수적 판정도 unknown이다. 계산용 명목 가정과 확인된 0mm를 구분한다.
“여유 있게 보기”의 제안 간격은 사용자 선택 조건으로 기록하며 제조사의 설치 기준으로 취급하지 않는다.
기존 `Tight`의 20mm는 표현용 기준이다. 공차·추천 간격·“딱 맞음” 판정 규칙으로 그대로 쓰지 않는다.
과소 공간, 명목 적합, 오차 포함 적합을 분리하고 경계 접촉과 여유 부족을 독립적으로 검사한다.

### 같은 상품의 N×M×K 격자

각 축의 사용 가능한 길이 S, 제품 길이 b, 양끝 여유 c₁/c₂, 사이 간격 g가 알려진 경우:

```text
n_max = max(0, floor((S - c₁ - c₂ + g) / (b + g)))
occupied(n) = n*b + (n-1)*g + c₁ + c₂     (n >= 1)
quantity = N*M*K
position(i,j,k) = (cx+i*(bx+gx), cy+j*(by+gy), cz+k*(bz+gz))
```

Rust checked arithmetic으로 계산하며 분모·음수 유효 공간·수량 overflow를 검사한다.
합성 예: 공간 60×40×40cm, 제품 20×20×20cm, 명목 간격 0이면 3×2×2=12개다.
같은 예에서 가로 양끝 5mm·사이 5mm를 요구하면 3개는 620mm로 초과하여 가로 최대 2개다.
이 예의 0/5mm는 계산 fixture 값이며 권장 설치 간격이나 적층 허용 근거가 아니다.
최대 격자만 보여 주지 않고 1≤N≤Nmax, 1≤M≤Mmax, 1≤K≤Kmax의 유효 격자를 cursor로 열거한다.
N=M=K=1은 단일 상품 그룹에 합치고, 동일 치수의 중복 회전도 제거한다.
K>1은 지지·적층 호환·최대 단수·하중을 검사한다. 공중 배치나 크기만 같은 임의 적층을 허용하지 않는다.
끼워 쌓는 제품은 확인된 stack pitch와 겹침 모델을 적용한다. 미지원이면 H를 임의로 줄이지 않는다.
적층 조건이 unknown이면 “쌓기 조건 확인 필요”인 개략 후보이며 검증된 조합과 분리한다.
M>1은 뒤쪽 제품을 꺼내는 경로를 별도 검사한다. 외경 fit이 접근 pass를 만들지 않는다.

### 혼합 조합과 독립 검증

실제 SKU를 먼저 선택하고 행·열·층으로 남은 직육면체 영역을 나누는 결정론적 DFS를 MVP에 사용한다.
서로 다른 제품의 나란히 놓기와 층별 배치를 생성하고 각 placement에 variant·orientation·좌표·support 참조를 붙인다.
같은 상품도 방향이 다른 배치는 혼합 배치로 검사한다. 상품 집합이 같아도 위치·접근성이 다르면 구별한다.
MVP 탐색 범위 제안은 혼합 **2종 이하·64개 이하·2층 이하**, 행/층 분할 패턴이다. 일반 3D 전체 탐색은 아니다.
더 큰 수량의 동일 상품 격자는 압축 표현으로 유지하고, 위 상한 때문에 단일 상품 검색에서 빠뜨리지 않는다.
남은 공간의 축 상한·부피 필요조건·확정 충돌·확정 금지 방향·수량 초과로 가지치기한다.
부피만 맞는 것은 충분조건이 아니다. 내경 unknown을 수납 용량 0으로 넣어 순위를 매기지 않는다.
상품 검색에는 top-K 제거를 적용하지 않는다. 혼합 beam/top-K를 쓸 경우 별도 불완전 프로필로 기록한다.
대칭 제거는 동일한 옵션·좌표 구조에만 적용한다. 판매처·가격이 다르다는 이유로 실물 후보를 없애지 않는다.
독립 validator가 `geometry.rs`의 경계·AABB 충돌·돌출, 방향·지지·적층·수량을 다시 확인한다.
외경, 내경/내용물, 설치, 개폐, 접근, 지지/하중, 수량을 각각 pass/fail/unknown/not_applicable로 반환한다.
내용물을 입력하지 않은 검색에서는 내용물 수납을 평가하지 않는다. 설치·개폐·접근 미측정은 unknown이다.
확정 fail은 추천에서 제외하며, unknown은 조건부 결과로 남긴다. AI 점수로 검사 결과를 바꿀 수 없다.

### 순위와 성능 경계

기본 순서는 확인 상태 → 필요한 추가 확인 수 → 남는 공간 → 확인된 비용 → 안정된 variant/배치 ID다.
남는 공간은 축별 mm와 외형 점유율로 설명한다. 외형 점유율을 실제 수납 용량이나 생활 편의 점수로 부르지 않는다.
조합의 주문량은 `quote_offer_bundle`에 연결한다. 필요한 3개/2개 묶음은 주문 2묶음·남는 1개다.
여러 SKU를 공간에 섞는 것과 판매자가 파는 이종 세트는 다르다. 기존 이종 bundle 미지원은 별도 확장 대상이다.
배송비·가격·재고 미확인은 순위에서 0원·구매 가능으로 간주하지 않는다. 확인된 소계와 미확인 항목을 함께 표시한다.
단일 상품은 O(V×R), R≤2로 전수 검사한다. 격자 결과 수와 혼합 상태 수는 별도로 커질 수 있다.
초기 제안 예산: 혼합 100,000 node, step당 1,000 node, 첫 화면 20개, 결과 메모리 64 MiB 목표.
모든 숫자는 벤치마크 전 제안이다. 한도 도달 시 결과를 버리거나 완료로 표시하지 않고 cursor를 보존한다.
`inputRevision/catalogDigest/ruleVersion/solverVersion/profile/budget/cursor`로 이어보기와 결과를 결속한다.
`complete/budget_exhausted/cancelled/catalog_partial` 및 검사한 상품·미탐색 shard·확장 node 수를 반환한다.
상품 전체 검사와 조합 탐색의 완료 상태를 따로 둔다. 한 번의 시간 초과로 “맞는 상품 없음”을 표시하지 않는다.
Worker는 step 사이에 task queue를 양보한다. 입력 변경·취소·버전 변경 시 과거 응답을 폐기하고 메모리를 해제한다.
목표는 캐시 5,000옵션에서 첫 단일 결과 p95 1초, 첫 조합 2초 이내다. 실제 모바일 측정 전 달성 주장하지 않는다.
선택한 안은 독립 검증 후 PlanSnapshot에 연결하며 도면·BOM·가이드는 같은 snapshot을 사용한다.

## 7. DeepSeek Flash 사용과 비용 제한

모델 의도는 **DeepSeek Flash**다. 실제 API model ID·제공 여부·가격·보존 정책은 배포 전 공식 자료로 확인한다.
미확인 모델 ID를 하드코딩하거나 다른 모델로 조용히 대체하지 않는다. AI 없이도 수집 규칙·검색은 작동한다.
`DEEPSEEK_API_KEY`는 서버 환경변수에서만 읽는다. VITE 변수·브라우저·확장·R2·저장소에 키를 넣지 않는다.
키·Authorization 헤더·전체 요청 객체는 성공/실패 로그·APM·예외·trace 어디에도 기록하지 않는다.

### 치수 추출

- 사이트별 규칙으로 읽히지 않는 짧은 사양 텍스트·옵션명만 서버로 보낸다. 전체 DOM·후기·사용자 정보는 보내지 않는다.
- 입력 텍스트는 비신뢰 데이터다. 그 안의 명령·URL 방문·도구 실행 지시는 무시하며 모델에 도구 권한을 주지 않는다.
- 출력은 축·단위·외경/내경/포장 역할·옵션 ID·근거 문자 위치·confidence 또는 abstain의 제한 JSON이다.
- 서버가 길이·enum·참조 범위를 검사하고 Rust가 수치와 원문 대응을 검증한다. 실패는 검토 큐로 보낸다.
- 높은 confidence도 확인 전이를 생략하지 않는다. 사람/독립 규칙 검증 전에는 반드시 unconfirmed다.

### 조합 순위

서버의 Rust가 카탈로그 기반 조합 템플릿을 만들고, AI는 제공된 ID들에 순서·제한된 이유 코드만 붙인다.
예: 두 종류의 나란히 놓기와 같은 종류 적층을 비교하되, 확인된 특징과 미확인 항목을 입력에 포함한다.
순위는 `catalogDigest + templateHash + prompt/modelVersion`에 고정하여 R2 release에 함께 게시한다.
브라우저는 해당 공간에서 Rust 검증을 통과한 후보에만 같은 검증 등급 안의 보조 순위를 적용한다.
AI가 본 적 없는 혼합 후보나 잘못된/누락된 ID는 결정론적 기본 정렬을 사용한다. 후보를 새로 만들거나 삭제하지 않는다.
이 방식으로 앱의 카탈로그·순위 읽기는 R2에 한정되고 사용자 공간 치수는 AI 서버로 전송되지 않는다.
실시간 개인화 순위는 MVP 범위 밖이다. 도입하려면 별도 데이터 전송 계약이 필요하다.

### 비용 가드

동일 `site/option/textHash/parserVersion/model/prompt`는 재호출하지 않는다. 무변경 재수집은 AI 비용 0회를 목표로 한다.
초기 제안 상한은 추출 1건당 입력 2,000/output 400 token, 순위 1회 50안·output 1,000 token이다.
서버에서 일/월 금액 한도·token 한도·동시성 2·30초 timeout을 강제하고 사용량 예약 후 호출한다.
검증된 단가표로 `입력 token×입력 단가 + 출력 token×출력 단가`를 집계한다. 구체 예산은 준태님 결정 사항이다.
단가 또는 사용량을 알 수 없거나 예산이 소진되면 AI를 중지한다. 실패 자동 재시도 없이 규칙 결과와 미확인을 유지한다.
운영 지표는 건수·token·비용·검토 전환율만 남기고 키·민감한 원문을 로그로 남기지 않는다.

## 8. R2 배치·갱신·복구

v1 `catalog/v1/<bundleId>/{bundle,manifest}.json`과 `latest.json`은 호환성 때문에 그대로 둔다.
새 상태와 shard를 기존 v1 enum에 끼워 넣지 않고 v2 reader/publisher를 추가하는 설계다.

```text
catalog/v2/latest.json
catalog/v2/releases/<releaseId>/manifest.json
catalog/v2/releases/<releaseId>/sources/<site>/part-0001.json
catalog/v2/releases/<releaseId>/ranking.json
catalog/v2/releases/<releaseId>/withdrawals.json
```

manifest는 schema·release·각 shard 경로/바이트/전체 SHA-256·건수·출처별 확인 시각·커버리지를 담는다.
원문 검토 큐·비밀·운영 로그는 공개 R2에 두지 않는다. 공개 근거는 허용된 짧은 사양 글자와 출처만 포함한다.
게시자는 Rust 검증이 끝난 immutable 객체를 올리고, manifest를 확인한 뒤 `latest.json`을 마지막에 교체한다.
single writer 락과 기대 이전 release 확인으로 동시 발행을 막는다. 실패하면 포인터를 유지하고 자동 재시도하지 않는다.
격리 행을 몰래 빼고 같은 배치를 성공으로 바꾸지 않는다. 원인 검토 후 제외 내역을 명시한 새 배치로 발행한다.
앱은 고정된 R2 HTTPS base의 GET만 사용한다. credentials omit, redirect error, no-referrer, 경로·크기 제한을 적용한다.
읽기 URL은 사용자에게 입력시키지 않는다. 운영 설정에서 지정하고 CORS는 앱 origin으로 제한한다.
latest 4 KiB, manifest 256 KiB, shard 1 MiB·최대 500옵션을 초기 제안으로 삼고 초과 시 분할한다.
기존 4 MiB snapshot/5 MiB 메시지 한도를 우회하지 않는다. shard별 검증·Worker 상주 index·선택 subset 전달 계약을 추가한다.
앱이 모든 shard의 길이·hash·버전·중복 ID를 검증해야 release 전체를 활성화한다. 부분 다운로드는 별도 상태다.
전체 release를 메모리에 복제하지 않고 IndexedDB에서 shard 단위로 처리한다. 용량 실패 시 이전 정상 버전을 유지한다.
R2 캐시 immutable 객체는 길게 보관하고 latest는 명시적 갱신 시 재확인한다. 조합 계산 도중 버전을 섞지 않는다.
첫 찾기와 “자료 새로고침”에서만 최신 포인터를 읽는다. 앱의 주기 polling·백그라운드 자동 재시도는 없다.
봇 재수집 제안 주기는 기존 기본 30일이며 최소 7일보다 촘촘하게 하지 않는다. API는 계약별 허용 주기를 따른다.
갱신 지연 시 마지막 관측일과 가격·재고 미확인을 표시한다. 목록에서 안 보인 것만으로 품절을 확정하지 않는다.
R2 장애 시 마지막 검증 캐시로 검색한다. 캐시가 없으면 “상품 자료를 아직 받지 못했어요”와 재시도 버튼을 제공한다.
철회·오규격은 새 release의 withdrawals로 신규 추천에서 제외한다. 과거 PlanSnapshot은 역사 자료로 보존하고 경고한다.
rollback은 기존 정상 release를 다시 가리키되 현재 철회 목록을 재적용한다. 삭제 의무가 있으면 별도 운영 절차로 수행한다.
구현 시 `connections.ts`, privacyOffline 검사, CSP/connect-src, CORS를 지정 R2 읽기에 한해 정합화한다.

## 9. 쉬운 한국어 UX와 접근성

입력은 한 화면의 세 숫자 칸과 한 주요 버튼이다. label은 “가로 / 깊이 / 높이”, 단위는 항상 cm로 보인다.
`inputMode="decimal"`, 명시적 label, 오류 연결, Enter 제출을 지원한다. 예시 숫자를 실제 입력값으로 미리 채우지 않는다.
“딱 맞음”은 **한 개로 놓는 후보** 그룹 이름이며 하단에 “입력한 크기 기준이에요”를 표시한다.
실제 여유는 “가로로 1cm 남아요”; 경계는 “여유가 거의 없어요”; 회전은 “옆으로 돌려 놓아요”로 설명한다.
미확인은 “치수 확인 중”, 적층 미확인은 “쌓아도 되는지 확인해 주세요”로 가까이 표시한다.
“조합”은 “옆으로 3개”, “앞뒤로 2줄”, “2단으로 쌓기”, “작은 것 2개 + 큰 것 1개”처럼 쓴다.
두 그룹 모두 확인된 후보를 먼저 보여 주고 조건부 후보는 접힌 영역으로 분리한다. 미확인을 초록 통과로 칠하지 않는다.
이미지 대신 Rust 좌표의 단순 정면/평면 SVG를 사용하고 제품명·수량·치수의 텍스트 대안을 제공한다.
모든 상품은 더 보기로 열람 가능하며, 정렬은 후보를 숨기지 않는다. 일부 탐색이면 “조합을 더 찾아볼 수 있어요”로 알린다.
0건은 “이 크기에 맞는 수납함을 아직 찾지 못했어요”로 쓰고 자료 부족·조건 제한·탐색 중단의 이유를 구분한다.
CSS는 `apps/web/src/styles/tokens.css`의 semantic token을 재사용한다. 카드 중첩·AI 배지·의미 없는 점수는 넣지 않는다.
쉬운 모드의 48px 이상 터치 대상, light/dark, 키보드 초점, 320/390px, 확대·forced-colors를 검증한다.
결과 변경은 `aria-live="polite"`, 입력 오류는 연결된 안내로 알린다. 새 자료 도착으로 포커스와 목록 순서를 갑자기 바꾸지 않는다.
구매 링크는 옵션·판매처·제휴 고지를 보여 준다. 가격 미확인은 “가격은 판매처에서 확인해 주세요”로 쓴다.
화면 생성·토큰 통과와 준태님의 화면 승인을 구분하고, 수용 근거 전까지 baseline은 draft다.

## 10. 테스트와 수용 기준

| 영역 | 필요한 검증 |
|---|---|
| 정규화 | cm↔mm, 소수·0·음수·상한·overflow, axis 뒤바뀜, unknown 보존 |
| 단일 fit | 정확한 경계, 1mm 부족/여유, 돌출, upright90만 가능, 금지/미확인 회전 |
| 공차/간격 | 공간 최소·제품 최대, 사이 n−1 간격, 이중 차감 방지, unknown≠0 |
| 격자 | N×M×K 모든 작은 조합을 독립 brute-force oracle과 대조, cursor 누락/중복 검사 |
| 혼합 | A+A+B, 서로 다른 높이, 충돌, 지지 없는 적층, 호환·하중 미확인, 뒤쪽 접근 |
| 수량/가격 | 필요 3/묶음 2, 판매처 배송 중복 방지, 품절, 가격·세금·배송 unknown |
| 수집 | 실제 허용 텍스트에서 만든 옵션 fixture, 포장/내경 혼동, 이미지 필드 유입 거부 |
| 확인 | AI high가 unconfirmed 유지, 무근거 confirmed 거절, 원문 변경 시 확인 무효화 |
| 보안/정책 | allowlist 이탈·redirect·robots 실패·403/429 중지·키 로그 차단·prompt injection |
| R2 | 잘못된 hash/길이/schema, 일부 shard 실패, 구버전 유지, 발행 중단, 철회·rollback |
| AI | 허위 ID·단위·근거 위치·JSON 거절, 예산·timeout·중복 cache, 실패 시 기본 순위 |
| UI | 숫자 세 개→결과, 입력 유지, 오프라인, stale 응답 차단, 더 보기, 조건부 문구 |
| 실행 대조 | 같은 fixture의 native Rust와 실제 브라우저 Worker/WASM 전체 정규 결과 일치 |
| 성능 | 100/1,000/5,000옵션, shard 증가, node 예산, 취소·재시작·메모리 회수, 실제 모바일 |

정확성 fixture는 합성 상품으로 만들고 실상품 수집·치수 대조 증거와 섞지 않는다.
MVP 수용에는 두 판매처별 실제 수집→확인→R2→브라우저 검색의 끝까지 연결한 증거가 필요하다.
허용 범위 전수 검사 및 미확인 분모, 같은 상품 격자와 서로 다른 상품 조합의 검증을 모두 포함한다.
구현 시 `cargo test`, 계약 생성 drift 검사, web typecheck/lint/test, 브라우저·parity를 변경 범위에 맞게 실행한다.
UI 구현 시 `node scripts/check-design-tokens.mjs --self-test`와 실제 화면 검증 결과를 별도로 기록한다.
이 문서 작성에서는 기능 테스트·브라우저·실사이트·API·R2 검증을 실행하지 않았다.

## 11. 단계와 마일스톤

| 단계 | 산출물 | 완료 조건 |
|---|---|---|
| M0 계약 | ALL 범위, v2 DTO, 네트워크 예외, 호스트·API 이용 조건 | 미해결 충돌 식별, 정책 정합성 및 실제 설정 확정 |
| M1 수집 MVP | 무인양품/다이소 확장 파서, 자동 큐, 확인 이력, AI 추출 adapter | 허용된 실물 옵션 텍스트 대조, 차단 중지, unconfirmed 전이 검증 |
| M2 자료 공급 | v2 R2 publisher/reader·shard·캐시·철회 | 원자적 발행과 장애 복구, 앱 카탈로그 읽기 목적지 R2 한정 |
| M3 검색 MVP | 3입력 UX, 전체 단일 검사, 격자, 제한된 혼합, 서버 AI 순위 | 두 결과 그룹·더 보기·unknown·native/WASM 대조·성능 근거 |
| M4 사용 수용 | 실제 두 판매처 여정, 모바일·접근성·화면 검토 | 수집/확인/검색 분모 공개, 준태님 사용 검수, 출시 판단 분리 |
| M5 판매처 확장 | 오늘의집→네이버→쿠팡→29cm→IKEA | 사이트별 권한·옵션·치수 근거와 동일 회귀 검사 |
| M6 조합 확대 | 더 많은 SKU/층·패턴, 점진 전수 열거 | 선언 범위 완전성 증명·작은 oracle 대조·대규모 비용 측정 |

MVP는 M1–M4이며 조합을 후속으로 모두 미루지 않는다. 실행 일정은 실상품 텍스트 확보와 검증량에 따라 정한다.
신규 판매처를 추가해도 기존 source 실패를 감추지 않는다. 미구현·미검증·조건부 항목을 완료 분모에서 빼지 않는다.
향후 구현 작업의 변경·검증·미완료·다음 작업은 IMPLEMENTATION_STATUS에 기록한다. 이번은 한 파일 지시에 따라 이 문서에만 남긴다.

## 12. 위험과 대응

- 수집량 확대와 권한 충돌: 허용 근거 없는 호스트는 비활성, 공식 API/feed 경로 검토, 출처별 철회 가능 구조.
- 치수가 이미지에만 존재: 미확인 유지, 허용된 사양 제공·실측 검토로 보충; AI가 치수를 창작하지 않음.
- 옵션·포장·뚜껑 혼동: 근거 범위와 필드 분리, 충돌 격리, 변경 시 확인 해제.
- 모든 혼합 조합의 폭증: 범위·cursor·예산 공개, 상품 전수 검색과 탐색 완전성을 별도로 계측.
- 공간은 맞지만 사용 불가: 적층·지지·개폐·접근 unknown을 표시하고 fail 후보는 추천 제외.
- “딱 맞음”의 과장: 그룹 설명과 축별 여유·미확인 문구를 가까이 배치하고 사용성 검수에서 오해 여부 확인.
- 순위·제휴 편향: AI는 검증 등급 내 보조 순위만 적용, 모든 일치 상품 접근 보장, 제휴 관계 명시.
- 데이터·요금·모델 변경: version pin, 갱신 날짜, 비용 차단, 규칙 기반 동작, 정상 release 복구.
- 자동 봇의 Chrome 가용성: 전용 실행 환경과 중단 기록, 갱신 지연 표시; 세션 우회로 정상처럼 가장하지 않음.

## 13. 준태님께 남기는 질문

1. MVP 혼합 범위를 2종·64개·2층으로 시작하고, 미탐색 범위와 이어보기를 표시하는 안을 채택할까요?
2. 첫 결과의 “딱 맞음”을 한 개 후보 그룹명으로 쓰되, “입력한 크기 기준”을 함께 쓰는 표현은 괜찮을까요?
3. 미확인 후보는 접어 두고, 외경 confirmed 제품을 우선 보여 주는 구성이 맞을까요?
4. 기본 여유는 명목 비교로 두고, “여유 있게 보기”에서 사용자가 간격을 선택하도록 할까요?
