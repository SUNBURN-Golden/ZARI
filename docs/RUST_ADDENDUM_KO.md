# 추가 지시문 — Rust 중심 정리컴파일러 아키텍처 v1.0

이 문서는 기존 ‘정리컴파일러 마스터프롬프트’에 덧붙이는 기술 변경 지시문이다. 별도 제품이나 별도 프로젝트를 새로 만들라는 뜻이 아니다.

## 1. 적용 우선순위

기존 마스터프롬프트의 제품 목표, IKEA·Elfa 레퍼런스, 사용자 여정, 지원 공간, 정리 전략, 기하학 규칙, 안전·불확실성 처리, 구매목록 요구사항은 유지한다.

다만 기존 9절의 데이터 계약, 17절의 기술 구성, 20절의 테스트, 21절의 개발 단계 중 아래 내용과 충돌하는 부분은 이 추가 지시문으로 대체한다.

최종 기술 방향:

- 핵심 도메인·정리 규칙·배치 탐색·적합성 검증·BOM 계산: Rust.
- 사용자 화면·입력·드래그·도면 표시: React + TypeScript.
- 브라우저 계산: Rust를 WebAssembly로 빌드하여 Web Worker에서 실행.
- 향후 서버 계산: 동일 Rust 코어의 네이티브 빌드 재사용.
- DuckDB·Polars: 필요성이 확인된 카탈로그·분석 작업에 선택적으로 사용.
- cuDF: GPU 데이터 처리의 효과가 검증된 경우에만 별도 실행 경로로 사용.
- Python: 필요시 GPU·외부 도구 어댑터에 한정. 핵심 판정 엔진을 Python으로 재작성하지 않는다.

‘Rust 중심’은 모든 화면을 Rust로 만들라는 의미가 아니다. ‘필요시 도입’은 처음부터 설치하고 비활성화하라는 의미도 아니다.

기존 구현이 있으면 먼저 조사하고 단계적으로 이전한다. 이 지시를 이유로 작동하는 화면·데이터·테스트를 무단 삭제하거나 전체 저장소를 갈아엎지 마라.

## 2. Rust 코어를 계산의 단일 기준으로 삼아라

다음 기능의 정식 구현은 Rust에 둔다.

1. 입력 정규화와 도메인 검증.
2. 단위 변환, 치수·오차·금액·수량 처리.
3. 정리 전략 규칙과 Recipe 평가.
4. 실제 상품 옵션을 사용하는 후보 생성과 배치 탐색.
5. 외경·내경·장애물·지지면·방향·설치·접근 검사.
6. 물건 배정과 수량 보존 검사.
7. 구매 묶음·필수 부품·재사용 수량·확인된 비용 계산.
8. 검사 결과, 대안 비교, PlanSnapshot 생성.
9. 도면·BOM·정리 가이드에서 공통으로 사용하는 구조화된 결과 생성.

TypeScript는 UI 상태, 선택, 임시 드래그 위치, 화면 좌표 변환, 표시 형식, 저장 어댑터를 담당한다.

UI의 빠른 입력 안내는 허용하지만 최종 판정을 대체하지 못한다. 임시 드래그 도형은 ‘검사 전 미리보기’로 취급하고 Rust 응답 전 확정 배치로 표시하지 않는다.

화면·서버·상품 처리 도구에 서로 다른 정식 충돌 검사나 구매 수량 계산을 만들지 마라. 독립 테스트용 단순 계산과 이전 검증용 임시 구현은 허용하되 운영 판정 경로와 구분한다.

향후 서버가 결제·주문 등 중요한 처리를 담당한다면 브라우저의 결과를 신뢰하지 말고 서버에서 입력·권한·카탈로그·가격을 다시 검증한다. 같은 Rust 코드를 사용한다는 사실만으로 클라이언트 결과가 신뢰되는 것은 아니다.

## 3. 최소 코드 구조와 의존성 방향

신규 저장소의 시작 구조는 다음 정도로 제한한다. 기존 구조가 있다면 같은 책임 경계를 적용하되 불필요한 이동은 하지 않는다.

```text
apps/web/             React·TypeScript UI, Worker 호스트, IndexedDB
crates/core/          도메인 계약, 규칙, 기하 검증, BOM
crates/solver/        후보 생성, 탐색, 대안 비교
crates/wasm/          JS와 Rust를 연결하는 얇은 바인딩
fixtures/            공통 입력·기대 결과·회귀 사례
```

상품 import 도구와 네이티브 실행기는 실제 구현할 때 추가한다. 미래 기능을 위한 빈 서비스·빈 crate를 대량 생성하지 마라.

의존성은 아래 방향을 따른다.

```text
UI → Worker → WASM adapter → solver → core
                         └────────→ core
향후 native adapter ─────→ solver / core
향후 catalog tool ───────→ core의 검증 계약
```

core와 solver에 DOM, 브라우저 저장소, 파일 시스템, 네트워크, DuckDB, Polars, CUDA, 웹 프레임워크를 결합하지 않는다. 외부 데이터와 설정은 검증된 입력으로 전달한다.

폴더를 분리하는 것만으로 만족하지 마라. Cargo의 직접·전이 의존성과 feature 활성화 결과까지 확인해 WASM 빌드에 네이티브 데이터 엔진이 끌려오지 않게 한다.

기본 웹앱 빌드와 코어 테스트에 DuckDB·Polars·Python·CUDA 설치를 요구하지 않는다. 여러 실행 경로가 생기면 CI에서 WASM·네이티브·선택적 데이터 작업의 feature 조합을 따로 검증한다.

Rust를 사용한다는 이유로 처음부터 no_std, 사용자 정의 메모리 할당기, 복잡한 제네릭 프레임워크를 강제하지 마라. 명확한 자료구조와 테스트 가능한 함수부터 시작한다.

## 4. 도메인 타입과 숫자 정확성

길이·좌표·금액·수량을 의미 없는 숫자 하나로 취급하지 않는다. Rust newtype과 검증된 생성자를 사용한다.

개념 예시:

```text
LengthMm        길이
PositionMm      위치 좌표
MoneyKrw        원화 금액
Quantity        물리적 개수
PackQuantity    판매 묶음당 개수
Measurement     값·오차 범위·출처
CheckResult     pass / fail / unknown / not_applicable
```

기존 규칙대로 치수의 기준 단위는 정수 mm, 초기 금액은 정수 KRW다. 소수 cm 입력은 명시적인 십진수 변환을 거쳐 mm로 정규화한다. 입력을 조용히 반올림하지 않는다.

정수의 폭과 허용 범위를 문서화한다. 면적·부피·금액 합산·수량 곱셈은 checked arithmetic과 충분한 중간 타입을 사용한다. overflow·underflow·0으로 나누기를 검출하고 구조화된 오류로 반환한다.

영속 데이터와 통신 계약에는 플랫폼에 따라 폭이 달라지는 usize/isize를 사용하지 않는다. 내부 인덱스로 사용하는 것은 허용한다.

JS 경계를 넘는 큰 정수는 정밀도를 잃지 않도록 표현을 고정한다. 기본안은 안전한 범위로 검증된 치수·수량은 number, 큰 금액·부피·카운터는 십진수 문자열이다. 다른 방식을 선택하면 JSON 저장·Worker 통신·스키마 생성까지 실제 round-trip을 검증한다.

렌더링의 픽셀 좌표나 비핵심 시각 효과에는 부동소수점을 사용할 수 있다. 다만 물리적 적합성, 금액, 수량 보존의 최종 판정을 부동소수점 근사에 맡기지 않는다.

unknown을 0으로 바꾸지 않는다. ‘내경 미상’, ‘수량 미상’, ‘무료’, ‘배송비 미확인’은 서로 다르게 표현한다.

Rust 타입이 있다는 이유로 JSON 역직렬화가 모든 도메인 조건을 자동 검증한다고 가정하지 마라. 입력이 항상 검증된 생성자 또는 명시적 validate 단계를 통과하도록 한다.

## 5. Rust–TypeScript 계약과 버전 관리

Rust 도메인 계약을 기준으로 공유 DTO를 정의하고 TypeScript 타입·스키마 생성 경로를 마련한다. 타입 생성 도구는 현재 호환성·유지보수 상태를 확인한 뒤 하나를 선택한다.

wasm-bindgen은 JS/WASM 연동에 사용하되, 임의의 Serde DTO 전체가 자동으로 정밀한 TypeScript 도메인 타입이 된다고 가정하지 마라. JsValue나 unknown으로 노출되는 경계는 별도 계약과 런타임 검증으로 보완한다. [T2]

프런트엔드의 Zod는 폼·입출력 경계의 검증에 사용할 수 있다. 그러나 Rust 모델과 독립적으로 관리하는 두 번째 도메인 정의를 만들지 않는다. 생성하거나, 동일 fixture와 계약 테스트로 불일치를 검출한다.

요청·결과에 필요한 버전 정보를 명시한다.

```text
schemaVersion
inputRevision
catalogVersion + catalogDigest
ruleVersion
solverVersion
searchProfile + searchBudget
seed: 난수 사용 시
```

requestId, 실행 시각, 소요 시간, 장치 정보는 관측 메타데이터로 분리한다.

카탈로그 digest는 동일 스냅샷 식별용이다. 해시가 있다고 상품 정보가 사실이거나 발행자가 인증되는 것은 아니다. 데이터 출처·검증 상태는 별도로 유지한다.

지원하지 않는 스키마 버전은 명확히 거절한다. 알 수 없는 enum이나 단위를 조용히 기본값으로 바꾸지 않는다.

## 6. WASM과 네이티브의 결과를 실제로 대조하라

같은 Rust 소스라는 이유만으로 실행 결과 일치를 선언하지 마라.

기본 탐색 모드는 결정론적 기준 모드로 둔다. 다음 조건을 고정한다.

- 정규화된 입력과 카탈로그 스냅샷.
- 규칙·solver 버전과 탐색 프로필.
- 후보 순서, 동률 해소 규칙, 필요한 난수 seed.
- 노드 확장 수 등 결정론적으로 정의한 탐색 예산.
- 정렬·직렬화·결과 정규화 규칙.

HashMap 순회 순서, 스레드 완료 순서, 현재 시각을 배치 선택 기준으로 사용하지 않는다. 병렬화하더라도 결과 선택 규칙을 명시한다.

벽시계 timeout은 사용자 응답성 보호 장치로 사용할 수 있다. 다만 timeout으로 중단된 결과를 같은 노드 예산을 끝까지 수행한 결과와 동일하다고 주장하지 않는다. 중단 원인과 소비한 탐색 예산을 반환한다.

네이티브와 실제 브라우저 WASM에서 같은 fixture를 실행해 배치, 물건 배정, 검사 상태, BOM, 정규화된 계획 내용을 비교한다. 생성 시각·실행 시간처럼 원래 달라지는 메타데이터는 비교 대상에서 분리한다.

추후 고성능 병렬 모드가 기준 모드와 다른 후보를 선택하도록 설계한다면 별도 프로필로 명시하고, 같은 결과라는 주장 대신 독립 검증 통과와 해 품질을 비교한다.

## 7. Worker 실행·취소·오래된 응답 처리

기본 실행은 Web Worker 하나 안에서 단일 스레드 WASM을 사용하는 방식으로 시작한다. [T1, T3]

처음부터 SharedArrayBuffer, 브라우저 다중 스레드, Rayon, 서버 병렬 처리를 필수 조건으로 만들지 않는다. 필요할 때 타깃 지원·브라우저 정책·배포 헤더와 실제 이득을 검토한다.

긴 탐색을 단일 동기 WASM 호출로 끝까지 실행하지 않도록 API를 설계한다. 다음은 책임을 설명하는 API 예시이며, 실제 이름은 저장소 계약에 맞게 확정한다.

```text
normalize_input(...)
propose_strategies(...)
start_search(...)
step_search(handle, node_budget)
validate_layout(...)
compute_bom(...)
dispose_search(handle)
```

탐색을 일정 작업량씩 수행하고 Worker의 작업 큐에 제어를 반환해 취소·새 입력 메시지를 처리할 수 있게 한다. cancel 메시지를 보내는 코드만 작성하고 취소가 된다고 판단하지 마라. 실제 긴 실행 중 취소 테스트를 작성한다. [T3]

JS 스케줄링은 새 메시지를 처리할 기회를 주어야 한다. 동기 루프나 마이크로태스크만 연속 실행하는 방식으로 이벤트 처리를 굶기지 않는다.

Worker 요청에는 projectId, requestId, inputRevision, catalogDigest를 포함한다. 현재 프로젝트·입력·카탈로그와 다른 응답은 최신 결과에 반영하지 않는다.

필요하면 Worker 종료·재생성으로 복구하되 마지막으로 확정된 프로젝트 데이터를 보존한다. 정상적인 잘못된 입력은 Rust Result 기반 오류로 처리하고 panic/trap을 정상 제어 흐름으로 사용하지 않는다.

WASM 탐색 핸들·메모리 수명을 명시한다. 검색 취소, 프로젝트 전환, Worker 재시작 시 자원이 해제되는지 확인한다.

## 8. 경계 통신과 상호작용 성능

첫 버전은 이해하기 쉬운 구조화된 DTO로 시작한다. 측정 없이 복잡한 바이너리 프로토콜부터 만들지 않는다.

동시에 다음 낭비는 피한다.

- 드래그 이벤트마다 전체 상품 카탈로그 직렬화.
- 충돌 검사 한 쌍마다 JS↔WASM 왕복.
- 매 프레임 모든 배치와 모든 설명 다시 계산.
- 카탈로그가 바뀌지 않았는데 전체 정규화 반복.

카탈로그·정규화된 공간은 Worker에 유지하고 변경분 또는 명확한 편집 명령을 전달하는 방식을 우선 검토한다. 단, 증분 갱신 후에도 revision과 전체 재검증 경로를 유지한다.

전체 import, 직렬화, Worker 메시지 복사, WASM 초기화, 탐색, 결과 렌더링 시간을 구분해 측정한다. 알고리즘 실행 시간만으로 앱 성능을 평가하지 마라.

더 빠른 직렬화나 TypedArray·Arrow 전달은 해당 경계가 병목으로 확인된 뒤 도입한다. 이름만 보고 zero-copy라고 주장하지 않는다.

## 9. 탐색기는 Rust, 적합성 검증기는 별도 책임

기존 ‘정리 전략→방식·스타일→실제 SKU와 배치의 공동 탐색’ 흐름을 유지한다. Rust 이전을 이유로 단순한 박스 채우기 문제로 축소하지 않는다.

초기 최적화는 다음 순서로 접근한다.

1. 명백히 불가능한 상품의 보수적 사전 제거.
2. Recipe와 사용자 선택을 반영한 후보 생성.
3. 기존 수납함 재사용·직접 배치 후보 포함.
4. 결정론적인 가지치기·후보 순서·제한된 backtracking.
5. 증분 검사와 반복 계산 캐시.
6. 프로파일링 후 자료구조·병렬화 검토.

후보 수를 줄여 빠르게 만들었으면 탐색 범위를 기록한다. 제한된 후보 탐색 실패를 전체 카탈로그에서의 불가능으로 표시하지 마라.

solver가 반환한 ‘통과’ 플래그를 그대로 믿지 않는다. 별도 validator가 실제 배치 좌표, 지지 관계, 내용물 배정, 수량을 다시 검사한다.

validator는 solver의 탐색 상태나 성공 플래그에 의존하지 않는다. 단위·좌표 같은 공통 기본형은 공유할 수 있으나 테스트에는 독립된 작은 기준 계산을 추가한다.

도면·BOM·가이드는 검증된 동일 PlanSnapshot에서 생성한다. 미배정 물건이나 검증 미완료 항목이 비용 계산 과정에서 사라지면 안 된다.

## 10. DuckDB 도입 정책

DuckDB는 네이티브 상품 데이터 도구에서 SQL 기반 조회·조인·집계·품질 점검·가격 이력 분석이 유용할 때 검토한다. Rust 연동은 공식 클라이언트의 현재 지원 범위를 확인한다. [T4]

다음은 도입 가능한 역할이지 초기 필수 기능이 아니다.

- 판매처별 상품·옵션·가격 관측 데이터 조회.
- 규격·재질·색상·검증 상태별 후보 추출.
- 중복 옵션과 누락 필드 점검.
- 시간별 가격·재고 관측 분석.
- 검증된 카탈로그 스냅샷 생성.

사용자 편집 상태와 프로젝트 저장을 DuckDB에 무조건 통합하지 않는다. 초기 IndexedDB 저장 방향은 유지한다.

DuckDB의 공식 Rust 클라이언트를 넣는 작업과 브라우저용 DuckDB-Wasm 도입은 별개로 판단한다. 브라우저에 SQL 분석 엔진이 필요하다는 근거가 없으면 추가하지 않는다.

DuckDB가 없어도 코어 빌드·fixture 실행·작은 카탈로그 정리 계획 생성이 가능해야 한다.

## 11. Polars 도입 정책

Polars는 Rust 기반 카탈로그 정제·변환 파이프라인에 실익이 있을 때 도입한다. 현재 Rust API와 필요한 feature만 확인해 사용한다. [T5]

검토 대상:

- 여러 공급사의 CSV·JSON·Parquet 변환.
- 치수 단위와 옵션 표현의 정규화.
- 상품·판매처·관측 데이터의 조인과 검증용 집계.
- 품질 점검 보고서와 카탈로그 배치 생성.

작은 데이터와 단순 변환은 일반 Rust 자료구조로 처리해도 된다. DuckDB와 Polars를 필수 세트로 취급하지 마라.

둘을 병행할 때는 어떤 작업을 어느 쪽이 맡는지 기록하고, 동일한 변환 규칙을 양쪽에 중복 구현하지 않는다.

원본→정제→도메인 검증→카탈로그 스냅샷의 경계를 둔다. 데이터프레임 처리 결과도 Rust의 도메인 검증을 통과해야 한다.

외경·내경·배송 박스 규격·색상 옵션·판매 묶음 수량을 혼동하지 않는다. 자동 추출한 값을 확인된 제조사 값으로 승격하지 않는다.

스냅샷에는 스키마, 출처, 확인 시각, 변환 버전, 행 식별 기준, 미확인 필드 상태를 보존한다.

## 12. cuDF 도입 정책

cuDF는 선택적 GPU 데이터 처리 도구이며 정리 배치 solver의 기본 엔진이 아니다.

현재 확인된 공식 Polars-cuDF 연동은 Python Lazy API 경로다. Rust Polars에 옵션 하나를 켜면 동일하게 전환된다고 가정하지 마라. 실제 도입 시 공식 지원·버전 호환성·GPU 및 OS 요구사항을 다시 확인한다. [T6, T7]

GPU 처리가 필요해지면 기본 검토 구조는 다음과 같다.

```text
Rust catalog tool
→ 버전이 명시된 배치 입력
→ 선택적 Python + Polars/cuDF 실행기
→ 결과 스키마·정수·null 의미·수량 검증
→ 검증된 카탈로그 스냅샷
```

새로운 Rust 직접 연동이 도입 시점에 존재한다면 공식성·지원 범위·라이선스·유지보수·호환성·실제 실행을 검토한 뒤 대안으로 비교할 수 있다. 이름이 비슷한 crate가 있다는 이유만으로 공식 지원으로 간주하지 않는다.

GPU 도입 전 다음을 모두 확인한다.

1. 실제 반복 업무에서 CPU 경로의 병목이 관측됐다.
2. 해당 연산과 데이터 형식이 선택한 GPU 경로에서 지원된다.
3. 데이터 읽기·전송·초기화·결과 회수까지 포함해 이득이 있다.
4. 필요한 필드·집계·null 처리에서 CPU 기준 결과와 의미가 일치한다.
5. 하드웨어·배포·유지보수 비용을 감수할 이유가 있다.

GPU를 요청했다는 사실과 실제 GPU에서 실행됐다는 사실을 구분한다. 미지원 연산의 CPU fallback 여부를 확인하고 기록한다. fallback한 실행을 GPU 벤치마크로 보고하지 않는다. [T6]

GPU 실패·메모리 부족·GPU 없음에 대한 명시적 CPU 대체 경로 또는 재시도 가능한 오류를 제공한다. 부분 생성된 카탈로그를 정상 버전으로 게시하지 않는다.

GPU 데이터 처리 서비스를 첫 실행·첫 배포의 선행 조건으로 만들지 않는다. 별도 승인 없이 유료 GPU 인프라를 생성하지 마라.

## 13. 도입 결정은 측정과 되돌리기까지 포함하라

DuckDB·Polars·cuDF·병렬화·새 직렬화 계층을 도입할 때 다음을 짧은 ADR로 기록한다.

```text
문제: 실제로 어떤 작업이 병목이거나 유지보수 부담인가?
기준선: 현재 구현, 입력 규모, 환경, 시간, 메모리.
대안: 일반 Rust 개선 / 도구 도입 / 데이터 구조 변경.
효과: 정확성, 지연시간, 처리량, 해 품질, 운영비.
복잡성: 의존성, 빌드, 배포, 디버깅, 장애 대응.
결정: 채택 / 보류 / 제거.
복구: 이 도구 없이 돌아가는 경로 또는 rollback 방법.
```

‘상품 1만 개면 무조건 GPU’처럼 임의의 행 수만으로 도입을 결정하지 않는다. 단순 필터와 복잡한 조인·집계·배치 탐색을 다른 작업으로 측정한다.

개발 환경, 실제 모바일 브라우저, 네이티브 실행을 구분한다. cold start와 warm run, p50과 p95, 최대 메모리, 샘플 수, WASM 크기, 해의 유효성과 품질을 함께 기록한다.

처음부터 최고 성능이라고 주장하지 마라. 이전 마스터프롬프트의 시간 목표는 측정 목표이며 완료 사실이 아니다.

## 14. 추가 테스트와 CI 완료 조건

기존 테스트를 삭제하지 말고 코어 관련 검증은 Rust로 이전·보강한다. TypeScript 테스트는 UI·계약·통합을 중심으로 유지한다.

필수 추가 검증:

- 정수 범위, 잘못된 단위, 음수 길이, overflow·underflow.
- 큰 금액·부피·카운터의 Rust↔JS↔저장 round-trip.
- 역직렬화가 도메인 검증을 우회하지 못함.
- 동일 입력의 네이티브·실제 브라우저 WASM 결과 대조.
- 후보 정렬·동률 해소·고정 탐색 예산의 재현성.
- 입력 변경 후 오래된 Worker 응답 차단.
- 긴 탐색 중 실제 취소와 이후 새 탐색 성공.
- 프로젝트 전환·Worker 종료·실패 후 메모리와 상태 복구.
- 드래그 수정 후 재검증과 도면·BOM의 일치.
- 합성 카탈로그와 실제 검증 상품의 출처 구분.
- 기본 WASM 경로에서 데이터 엔진·GPU 의존성이 활성화되지 않음.
- 선택적 데이터 도구 실패 후 마지막 정상 스냅샷 보존.

Rust 단위·통합 테스트와 proptest 같은 속성 테스트를 검토한다. 브라우저는 Playwright로 실제 WASM 모듈을 로드한다. Rust 응답을 전부 mock한 테스트만으로 통합 완료를 주장하지 않는다.

CI에는 실제 저장소 구성에 맞는 다음 검사군을 마련한다.

```text
Rust fmt / clippy / native tests
WASM target build
공유 계약 생성·변경 감지
프런트 typecheck / lint / tests / build
실제 Worker + WASM 브라우저 통합 테스트
native ↔ WASM 공통 fixture 대조
```

Rust toolchain, JS 패키지, WASM 바인딩 도구의 호환 버전을 확인하고 lockfile과 재현 가능한 빌드 명령을 남긴다. optional feature는 지원 조합별로 별도 검사한다.

실행하지 못한 테스트와 성능 측정은 ‘미실행’으로 기록한다. 테스트 삭제·약화·가짜 성공으로 통과시키지 않는다.

## 15. 실제 적용 순서

아직 구현 전이면:

A. Rust core와 WASM 바인딩을 최소 구성한다.
B. 공간 경계 검사 1개와 구매 묶음 계산 1개를 Rust로 만든다.
C. 같은 fixture를 네이티브와 브라우저 Worker에서 실행한다.
D. React 화면의 입력→Rust 계산→도면·BOM 표시를 연결한다.
E. 그다음 기존 1단계 사용자 흐름 전체를 완성한다.

이미 TypeScript 구현이 있다면:

A. 현재 기능·테스트·저장 데이터 형식을 먼저 확인한다.
B. 유지할 UI와 이전할 계산 로직의 경계를 기록한다.
C. 기존 입력·기대 결과를 fixture로 고정한다.
D. 단위·기하·수량 계산부터 Rust로 옮기고 결과를 대조한다.
E. Worker/WASM 경로를 실제 UI에 연결한다.
F. 검증된 기능부터 기존 운영 계산 경로를 교체한다.
G. 안정화 후 중복 TypeScript 도메인 계산을 제거한다.

한 번에 전부 다시 쓰지 않는다. 장기간 두 개의 정식 계산 엔진을 병행하지도 않는다. 임시 비교 구현은 제거 조건과 시점을 기록한다.

첫 완료 게이트는 ‘Rust 프로젝트 생성’이 아니다.

‘사용자가 공간 치수를 바꾸면 실제 Rust/WASM이 다시 계산하고, 검증된 도면과 구매목록이 함께 갱신되며, 저장·불러오기가 유지되는 상태’다.

## 16. 이 추가 지시문을 받은 뒤 할 일

기존 마스터프롬프트와 이 추가문을 통합해 PRODUCT_SPEC, ARCHITECTURE, AGENTS, IMPLEMENTATION_STATUS를 필요한 부분만 수정한다.

코드 실행 환경이 있으면 위 최소 Rust/WASM 연결부터 구현하고 실제 실행 결과를 보고한다. 설명·폴더 생성·빌드 성공만으로 사용자 흐름 완료를 주장하지 않는다.

보고에는 변경한 파일, 실행 명령, 테스트 결과, 실제 연결된 UI 기능, 남은 제약을 포함한다. 선택적 데이터 도구를 아직 도입하지 않았다는 사실은 누락이 아니라 설계 상태로 기록한다.

지금 단계에서 DuckDB·Polars·cuDF가 불필요하다면 설치하지 않고 보류하라. 그 대신 나중에 검증된 카탈로그 스냅샷을 공급할 수 있는 데이터 계약은 유지한다.

최종 원칙:

‘정리의 판단과 검증은 Rust에 모으고, 화면은 사용하기 쉽게 만들며, 데이터 도구와 GPU는 측정된 필요에만 사용한다.’
